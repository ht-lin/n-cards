# 0001. 采用 ADR 记录架构决策

- **Status**: Accepted
- **Date**: 2026-08-25
- **Deciders**: 技术负责人
- **规格引用**: §13.7

## Context

NCards 是 3 个月 / 4 人的项目（§3.11），排期没有余量。规格书 v1.1 的 §2 已经沉淀了 11 条架构决策，但项目开工后还会持续产生新决策：引入新的第三方服务、调整同步语义、增加跨模块依赖。

这类决策的共同特点是**决策成本低、返工成本极高**，而且理由往往只存在于当时在场者的记忆里。三个月后有人问"为什么 `sort_order` 在 `card_members` 上而不在 `cards` 上"，如果答案只能靠考古 git log 或问人，就会出现两种坏结果：要么按错误的理解继续开发，要么把已经想清楚的问题重新讨论一遍。

同时，部分决策带有**合规义务**：引入新的第三方服务意味着新增 GDPR 子处理者（§8.3），必须有可追溯的记录以应对 Art. 30 的问责要求。

## Decision

我们采用 Michael Nygard 风格的架构决策记录（ADR），存放于 `docs/adr/NNNN-title.md`，与代码同仓、同 PR 流程 review。

模板固定为 `Context / Decision / Consequences / Alternatives considered / Status`。触发条件、编号规则与审批要求见 [`docs/adr/README.md`](README.md)。

ADR 只增不改：推翻旧决策要写新 ADR 并把旧的标为 `Superseded`。

## Consequences

**正面**

- 决策理由与代码同版本演进，`git blame` 能从一行代码追到它背后的决策。
- 新人（以及三个月后的自己）读 `docs/adr/` 就能补齐上下文，不必打断他人。
- GDPR 子处理者的引入有了天然的审计痕迹。
- "写下来"这个动作本身会过滤掉一部分想当然的决策。

**负面**

- 每条决策多出 20–40 分钟的写作成本，在 12 周排期里不是零。
- 存在流于形式的风险：事后补写的 ADR 只写"我们决定了 X"而不写取舍，价值接近于零。模板中的 **Alternatives considered** 与"必须写负面后果"是对此的部分防御，但最终靠 review 时较真。
- ADR 会过时。缓解手段是 `Superseded` 状态而非删除 —— 代价是目录会越来越长。

## Alternatives considered

- **只靠规格书 §2**：规格书是一份需要整体一致性的文档，往里塞增量决策会让它越来越难读，而且改规格书的门槛（`docs(spec):` PR + 全文一致性）高于写一篇独立 ADR，实际结果就是没人改，决策散落在 PR 讨论里。
- **Wiki / Notion**：脱离版本控制，无法与代码变更原子地一起 review，且离开仓库后天然会腐烂。本项目的合规要求也倾向于把记录留在可审计的单一位置。
- **PR 描述即记录**：PR 面向"这次改了什么"，不面向"为什么这样定"；搜索一个三个月前的决策要翻几百条 PR，实际不可行。
- **不记录**：最省事，也是默认会发生的事。代价在项目后期集中爆发 —— 那正是最没有时间返工的阶段。
