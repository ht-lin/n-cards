# 0013. Q3 定案：发信走 n-cards.de 的域名邮箱（dogado），不引入专业 ESP

- **Status**: Accepted
- **Date**: 2026-09-05
- **Deciders**: 创始人（商务）+ 后端负责人（落地）
- **规格引用**: §3.2、§8.3、§9.3、§14.4、§15.1、§17.5（Q3）、R1、T11
- **取代**: [ADR-0012](0012-mail-channel-topology.md) 的**决定 1**（「Q3 不在本 PR 内决定」）。
  ADR-0012 的其余三个决定（Doctrine transport、消息体加密、两个 deptrac 图层）**全部不受影响**
- **影响**：T-102（DNS 与送达验证两条尾巴解除阻塞）、T-450（隐私声明的子处理者清单）、
  T-405（`email_send_total{provider}` 的取值）、T-406（`esp-failover.md` 的升级路径）

> **补记 2026-09-06（决定不变，两项未解决项有进展）**
>
> - **未解决项 a（DKIM）基本落地**：`n-cards.de` 的 zone 里已有 dogado 自动写入的
>   DKIM 公钥，selector `cloudpit`（1024 位 RSA），SPF 也已自动写入
>   （`include:secure-mailgate.com`）。头号风险「dogado 不支持 DKIM」不成立，
>   `p=reject` 的路径保持打开。**仍须实发一封验证 `d=n-cards.de`**，见
>   [`email-dns.md`](../runbooks/email-dns.md) §2.4。
> - **新增未解决项 f**：套餐确认为 **1 个邮箱账号 + 只能收信的别名**，
>   于是「唯一那个可发信地址叫什么」成了一道取舍。详见下方未解决项表。
> - 配额（未解决项 b）与 AVV（c）**没有进展**，仍是本决定最大的两个未知。

## Context

Q3（§17.5「邮件服务商最终选型」）的截止日写的是 M0 结束，早已过期。
ADR-0012 当时的处理是**悬置**：代码保持通道无关，`MAIL_PROVIDER=unset`，
把两条交付物显式记账顺延。那个处理解除了 T-103～T-106 的阻塞，但没有解除
§15.1 的**上线必需项**——「向 Gmail / GMX / Web.de / Outlook 各发一封 OTP」——
的阻塞，因为没有真实通道就没得测。

现在选型定了：**用 n-cards.de 这个域名自带的邮箱（托管方 dogado GmbH，多特蒙德），
不采购 Brevo / Mailjet / Postmark 这类专业 ESP。**

需要先厘清一件容易被误读的事：**这不是对 §3.2 的偏离，恰恰是 §3.2 写的东西。**
§3.2 在 v1.1 里已经把 v1.0 的「专业 ESP 强制」撤销了，原文那张表第一行写的是：

> 发信通道：~~专业 ESP（EU）强制，禁 SMTP 直发~~ → **普通商业邮箱服务**
> （走其 SMTP 或 API 均可），仅要求**数据处理在 EU/EEA 内**

真正遗留的问题是 §17.5 的 Q3 与 `docs/runbooks/email-dns.md` 仍然只列了三家 ESP 作为候选，
以及 §8.3 的子处理者行还写着「商业邮件服务商（候选 Brevo FR / Mailjet FR / Postmark EU）」。
本 ADR 把这条口径统一到 §3.2 已经定下的那一档。

## Decision

**发信通道 = n-cards.de 的域名邮箱，SMTP submission（587 / STARTTLS），托管方 dogado GmbH。**

- `MAIL_PROVIDER=dogado`（`unset` 这个占位值退役）
- `MAILER_DSN=smtp://<邮箱账号>:<口令>@<dogado 面板给出的 SMTP 主机>:587`，
  仍然是凭据，仍然只走 sops(age)
- `MailSenderInterface` 以上**一行代码都不改**。这正是 ADR-0012 决定 4 那两个
  deptrac 图层要保证的事，本次换选型是对那层抽象的第一次真实检验，它通过了

### 三条合规硬要求逐条核对（§8.3，不可放宽）

| # | 要求 | dogado 域名邮箱 |
|---|---|---|
| ① | 数据处理在 EU/EEA | ✅ dogado GmbH，德国多特蒙德，机房在德国 |
| ② | 可签 AVV / DPA | ✅ 德国托管商的标准动作（Art. 28 AVV）。**仍须实际签署并归档** |
| ③ | 支持自定义域 SPF / DKIM | ✅ 两条都已自动写入我们的 zone（SPF `include:secure-mailgate.com`；DKIM selector `cloudpit`）。**待实发验证 `d=` 对齐**，见补记与未解决项 a |

> ⚠️ **这不是 §8.3 禁止的那种邮箱。** 那条禁令针对的是**个人 / 消费级邮箱账户**
> （Gmail、GMX 个人账户）与**美国 SaaS 的免费层**，禁的理由是「无 AVV 的第三国传输」。
> n-cards.de 的域名邮箱是一份**有合同、有 AVV、处理地在德国**的商业托管服务，
> 三条硬要求一条不缺。判据从来不是「是不是 ESP」，是那三条。

## Consequences

### 正面

- **子处理者少一家。** §8.3 原本要新增一家 ESP，现在是 dogado GmbH 一家德国托管商，
  且与 Hetzner 同属「德国境内、无第三国传输」那一档。§8.4 的隐私声明、T-450 的法律页面
  都少一段要写的东西，Art. 28 也少签一份合同。
- **零第三国传输叙事保持完整。** §14.1 / ADR-07 把「数据 100% 留在德国」当作营销点，
  引一家法国 ESP 虽然合规，但会让那句话需要加脚注。现在不用。
- **成本与采购动作为零。** 域名邮箱已经随域名在手，不需要新账号、新账单、新合同谈判。
- **`MAILER_DSN` 是标准 SMTP DSN。** 没有服务商 SDK、没有 API key、没有 webhook 端点，
  ADR-0012 决定 4 那道墙后面的东西反而更少。

### 负面 / 必须记账

这一段是本 ADR 存在的主要理由。**换到域名邮箱买到的是合规与成本，付出的是送达能力**，
而 §3.2 已经把「送达」定成了全站登录的单点（R1，影响「致命」）。

1. **有发信量上限，且上限未知。** 共享托管的邮箱几乎都有每小时 / 每天的发信配额，
   超过即被限流或临时停用。**dogado 的具体数字还没查**（见「未解决项」）。
   在查到之前，`ncards.mail.daily_warn_threshold` / `daily_breaker_threshold`
   从 3000 / 10000 下调到 **200 / 500** —— 宁可熔断误伤安全提醒，
   也不能让发信账号被托管商停掉，那是 R1 的直接触发。

2. **⚠️ §9.3 的容量目标已经越过这个上限。** `ncards_mail.yaml` 里按 5 万注册推算的
   日发信量是**约 1100 封**，而典型域名邮箱的日配额在几百这个量级。
   也就是说：**这个通道能撑住上线，撑不住 §9.3 的 12 个月目标。**
   这不是缺陷，是一个有明确触发条件的**已知天花板** ——
   `email_send_total` 的日累计逼近实测配额的 50% 就是重启本决定的信号，
   处置是按 §3.2 原方案补做专业 ESP（预计 2 人日，抽象层已就位）。
   该判据写进 [`docs/runbooks/email-dns.md`](../runbooks/email-dns.md) §4。

3. **共享 IP 声誉，且不由我们控制。** 专业 ESP 会为事务邮件维护发信 IP 池并处理投诉；
   共享托管的出口 IP 上还有别的租户，其中任何一个发垃圾邮件都会连累我们的送达率，
   而我们除了「换通道」没有任何干预手段。SPF/DKIM/DMARC 因此从「重要」升级为
   **唯一可控的送达手段**，`p=reject` 的推进不能省。

4. **没有 bounce / 投诉反馈回路，也没有抑制名单（suppression list）。**
   ESP 会告诉你哪个地址退信、哪个用户点了「举报垃圾邮件」，并自动停发。
   域名邮箱不会——退信只会以 SMTP 错误或一封退信信的形式出现，前者进
   `email_failed` 队列，后者进 `no-reply@` 的收件箱而没人看。
   §3.2 已经把「送达率 / bounce 监控体系」列为后置项，本决定使这条后置**更贵**：
   一期的唯一代理指标仍然只有 §14.4 的「OTP 转化率骤降」P1 告警。

5. **无投递 webhook，§14.4 那条「一期不测量」的理由变得更硬。** 规格里
   「OTP 邮件时延（发送 → ESP 确认投递）」标的是「需要接入服务商的投递 webhook」——
   域名邮箱根本没有这个东西，所以这条指标在本决定下**不是后置，是不可得**。

6. **`no-reply@n-cards.de` 会真实存在一个收件箱。** ESP 的发信地址通常是纯发信的；
   域名邮箱是双向的。后果有两个：① 用户回信会进那个箱子而没人看
   —— 模板里已经写了「请勿回复」，但仍应在 dogado 面板给它配一条自动回复或转发；
   ② 那个收件箱会积累**真实用户邮箱地址**（退信、误回复），
   而 §8.2 的 ROPA 里**没有这条数据流**。这是一个需要在 T-450 之前处理掉的合规缺口，
   已记进「未解决项」。

   **补记 2026-09-06：套餐只有 1 个账号，这条的后果比原先写的更重。**
   所有收信别名（`info@` / `datenschutz@` / `impressum@` / `dmarc@` …）默认都汇进
   **同一个收件箱**。于是那个箱子会同时是「设计上没人看的退信池」和
   「有 30 天法定 SLA 的信箱」（§8.5 数据主体权利、§5 DDG 的 Impressum 联系地址）。
   ⚠️ **法定地址的转发目标必须与 `no-reply@` 分开**，否则 Art. 15/17/18 的请求
   会被埋在退信里错过时限。归未解决项 d，且转发目标同样受 §8.3 约束
   （不能转去 Gmail —— 那是第三国传输，正是本决定要避免的）。

7. **staging 与生产共用同一个发信域和同一个邮箱账号。** `ncards_staging/main.yml`
   里那段「staging 用生产发信域」的理由（要测的就是生产那套 SPF/DKIM 与域名声誉）
   仍然成立，但现在两个环境还会**共享同一份发信配额**。staging 量级是每天个位数，
   可接受；真跑压测就会吃掉生产额度，这一点写进 runbook。

## Alternatives considered

**Brevo FR / Mailjet FR / Postmark EU（ADR-0012 时的三家候选）。**
它们在送达能力上全面胜出：专用事务 IP、bounce/FBL 回路、抑制名单、投递 webhook、
面板里现成的 DKIM。输在三点：多一家子处理者与一份要签的 AVV；
多一条「数据出德国」的脚注（Brevo/Mailjet 在法国，仍是 EU/EEA 内、完全合规，
但削弱 §14.1 的营销叙事）；以及一期真实量级下这些能力全部用不上 ——
§3.2 已经算过这笔账，结论是「期望损失低于现在就投入的成本」。
**保留为升级路径**：负面影响 2 那条触发条件一旦命中，就回来选它们。

**在 Hetzner 那台主机上自建 MTA（Postfix）。** 零子处理者，理论上最干净。
输得最惨：Hetzner 云主机默认封 25 端口出站（要开工单），新 IP 无发信信誉，
反垃圾规则对「单机新 IP 直发」几乎默认不信任，且我们要自己维护一个面向公网的 MTA
——那是一个新的攻击面与一份新的运维负担，而 §3.11 已经在为「3 个月 / 3–5 人」削减范围。

**继续悬置 Q3。** 输在它挡着 §15.1 的上线必需项。ADR-0012 悬置时给的理由是
「前两条硬要求是商务动作，后端替它挑一个只会制造假象」——那个理由在**创始人已经做出
选择**之后就不成立了。本次决定正是那个商务动作。
