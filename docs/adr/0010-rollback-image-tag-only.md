# 0010. 自动回滚只回镜像 tag，迁移不自动回滚；部署前快照是护栏不是备份

- **Status**: Accepted
- **Date**: 2026-09-02
- **Deciders**: 全员（T-012）
- **规格引用**: §9.4、§13.5、§14.3
- **影响**：**从 M1 起所有带 Doctrine 迁移的后端任务**，以及 T-406（备份体系）

## Context

§14.3 的生产发布流程写着：

> 选择 sha → 备份数据库（前置快照）→ 滚动重启 app/worker → 执行迁移
> → 健康检查 → **若失败自动回滚到上一镜像 tag**

「自动回滚」四个字底下藏着两个没被回答的问题，T-012 落地时必须回答：

1. **回滚要不要连数据库一起回？** 迁移已经跑过了。回滚镜像但不回 schema，
   意味着旧镜像要跑在新 schema 上；连 schema 一起回，意味着自动执行 `down()`。
2. **「前置快照」到底是什么？** §7.4 与 §14.2 要求的备份是 pgBackRest / wal-g
   + age 客户端加密 + Hetzner Storage Box + 保留 30 天 + 每季度恢复演练 ——
   那是 T-406 的交付物，T-012 时它还不存在。

同时，健康检查还有第三种结果要处理：ADR-0004 的人工 unseal 意味着主机重启后
Vault 是**封印**的，此时 `/health/ready` 返回 503 —— 而那是期望行为，不是故障。

## Decision

**一、自动回滚只把 `.env` 里的 `APP_IMAGE` 换回上一个 tag，重启 `app`，重新判定。**

上一个 tag 记在目标主机的 `/opt/ncards/state/previous-image`，在改 `.env`
**之前**写入。状态必须在主机上而不是流水线的内存里 —— CI runner 是无状态的，
而失败完全可能发生在 `.env` 已被覆盖之后。

回滚只重启 `app`，**不动 postgres / redis / vault**。尤其是 vault：重启它会让它
重新封印，于是一次自动恢复会变成一次需要三个人到场的人工事故。

**二、迁移不自动回滚。**

最常见的失败形态是「迁移成功了、应用起不来」。此时自动跑 `down()` 会删掉刚加的列 ——
把一个**可修复**的故障变成**数据丢失**。数据层的兜底是部署前的快照，
要不要恢复是人工决策，步骤在 `docs/runbooks/deploy-and-rollback.md`。

**三、部署前快照 = 简易 `pg_dump | gzip` 到主机本地 `/var/backups/ncards/`。**

保留最近 10 份，0600 / 目录 0700 / owner root —— 防的是将来多出来的非特权用户与
挂错卷的容器。**它挡不住 deploy 用户**（有 sudo，且在 docker 组里 ≡ root，
见 [ADR-0009](0009-ansible-sops-deploy-topology.md)），别把它当成访问控制。
它是**发布护栏**，明确**不是**备份系统。

**四、健康判定分三级，`vault_sealed` 不触发回滚。**

| 判定 | 判据 | 动作 |
|---|---|---|
| `ok` | `/health/live` 200 且 `/health/ready` 200 | 成功，清理旧镜像 |
| `vault_sealed` | live 200、ready 503、`vault status` 退出码 1 或 2 | **不回滚**，job 红，等人工 unseal |
| `broken` | 其余情况 | 回滚 → 重新判定 → 无论结果 job 都红 |

## Consequences

### ⚠️ 对所有后续后端任务的硬性要求

**自动回滚要成立，上一个镜像必须能跑在新 schema 上。** 而 §14.3 把顺序定成
「重启 → 迁移」，于是**新镜像也必须能跑在旧 schema 上**。两头都要求向后兼容，
落到实处就是一条规矩：

> **从 M1 起，所有 Doctrine 迁移必须遵守 expand-contract：**
> 先只做加法（可空列、新表、新索引），删列 / 改类型 / 加非空约束一律推到
> **下一次**发布，且要确认上一版应用已经不再依赖被删的东西。

§9.4 已经要求「每个 migration 必须实现可用的 `down()`」—— 那条仍然有效
（人工回滚时要用），但 `down()` 存在**不等于**它会被自动执行。这两件事以前
容易被混为一谈，这条 ADR 把它们分开。

不写下来的后果很具体：某天一条「顺手把 `nullable` 改成 `NOT NULL`」的迁移合进去，
部署时应用崩了，自动回滚把镜像换回上一版 —— 上一版往那列写 NULL，于是回滚之后
仍然是坏的，而现场看起来像「回滚没用」。

### 快照的四条负面后果

1. **无异地、无 WAL 归档、无客户端加密。** 它不满足 §7.4 / §14.2 的任何一条备份
   要求。RPO ≤ 15 分钟（§9.4）靠它是达不到的 —— 它只在部署那一刻存在。
2. **⚠️ 生产上，未加密的 `pg_dump` 落在业务主机磁盘上是真实的合规缺口。**
   缓解只有目录权限（0700 / root）。**生产真正启用前，必须先由 T-406 的
   age 加密 + Storage Box 方案替换本步骤。** 这句话同时写在
   `inventory/group_vars/ncards_production/main.yml`、快照任务的头注释、
   以及 `docs/tasks/M0.md` 的交付产物段 —— 三处，因为它很容易被忘掉。
3. staging 上不存在第 2 条的缺口：只有合成数据，没有个人数据（§14.1）。
4. **⚠️⚠️ `vault_data` 卷完全没有备份 —— 全仓任何地方都没有。**
   见下节，这是本次交付**最严重的未缓解风险**。

### ⚠️ `vault_data` 没有被本决策覆盖，而且当前完全没有备份

**本决策的快照只有 Postgres。** `vault_data` 不在里面 —— 这一点是刻意的且正确的：
部署流程根本不碰那个卷（`up -d` 不删卷，回滚只重启 `app`），把它塞进每次部署的
快照既解决不了这份快照要解决的问题，又在 40 GB 的盘上反复写。

**但由此暴露一件必须写下来的事：T-012 交付后，`vault_data` 在任何地方都没有备份。**
§9.4 是明确要求的：

> **Vault 数据丢失 = 全部卡数据不可解密**，因此 Vault 存储卷单独每日快照。

它归 T-406（compose 里的 `backup` 服务目前还是注释），范围划分没错 ——
**但风险从 T-012 落地那天起就存在**，而不是等到 T-406 才开始。

严重程度分环境：

- **staging**：合成数据。丢了就是重新 `operator init` + `bootstrap.sh` + 重签
  AppRole，麻烦，不致命。
- **生产**：丢了 = **全部卡数据永久不可解密**。
  ⚠️ **unseal key 救不了你** —— 它解的是 master key，而 master key 解的是那个卷。
  卷没了，5 把 key 拼齐也没有任何东西可解。这一点很容易被
  「unseal key 离线存了 ≥2 个物理位置」的说法掩盖过去：**那保的是可用性，
  不是持久性。**

**给 T-406 的技术前提**（现在就该知道，免得到时才发现）：
`infra/vault/vault.hcl` 用的是 **`file` 后端，不是 raft** ——
所以 `vault operator raft snapshot` **用不了**，那是 raft 专有命令。
而 Vault 运行期间直接 `cp -r /vault/file` 不保证一致性。可行的两条路：
停 Vault 再拷，或走文件系统 / Hetzner 卷级快照。无论哪条，
**都必须配一次真实的恢复演练**（§9.4 每季度一次，且「未演练的备份视为不存在」）。

### 其他

- **`vault_sealed` 时 job 会红，但不会自愈。** 这是刻意的：staging 确实不可用，
  不该看起来像没事；但回滚是错误的动作。错误信息带 `VAULT_SEALED` 前缀并直接
  指向 `docs/runbooks/vault-unseal.md`。代价是主机重启后的第一次部署一定是红的 ——
  在有人 unseal 之前，任何流水线都没法让它变绿。
- **回滚深度是 2 步。** 只记一个 `previous-image`，镜像保留 3 个。要回到更早的
  版本得用 `deploy-manual.yml` 显式指定 sha（那个镜像可能已经被清理掉了，
  但 GHCR 上还在，会重新拉）。
- **首次部署失败时无法回滚**（没有「上一个」）。`rollback.yml` 会带着明确的
  说明失败，而不是把 `.env` 写成空的 `APP_IMAGE`。
- **⚠️ 生产的 approval 门当前是可绕过的**（未缓解）。本决策原本假设生产发布由
  `production` Environment 的 required reviewers 守着，但那条保护规则在
  **Free 计划的私有仓库上建不出来**（GitHub API 明确以 billing plan 拒绝）。
  同一个 Environment 上另外两项 Free 可用、且已经配上：
  **Deployment branches = 仅 `main`**，以及生产密钥用 environment secret 隔离。
  只有 approval 降级成了 `deploy-manual.yml` guard 里的输入确认串
  （必须原样输入 `deploy-production`）+ 「`image_tag` 必须是 `origin/main` 的祖先」。

  **降级掉的是「不可绕过」这个性质**，不是「第二个人把关」—— 单人仓库上
  required reviewers 的实际效果本来也只是同一个人再点一次
  （reviewer 是自己，且 Prevent self-review 必须关掉，否则永远无人可批）。
  确认串拦得住选错环境（`environment` 默认 staging，与 production 只差一个下拉项，
  这是最可能发生的事故），拦不住账号被盗或有人直接改 workflow。

  **解除条件**：账号升 GitHub Pro，或仓库转 public。之后配上 required reviewers、
  删掉 guard 里的确认串那一步；**祖先校验那步要留着** —— Environment 的分支策略
  只约束触发时选的 ref，管不到 `image_tag`，那个缺口任何计划下都存在。

## Alternatives considered

**1. 回滚时自动执行 `doctrine:migrations:migrate prev`。** 表面上更完整。
输在它把最常见的故障（迁移成功、应用启动失败）的后果从「重启一下就好」放大成
「刚写进去的数据没了」。而且 `down()` 的质量在现实中**永远**低于 `up()` ——
它极少被真的执行过，把它放进无人值守的自动路径是拿数据赌一段没测过的代码。

**2. 迁移前后各做一次快照，失败时自动 restore。** 单主机上 restore 要停写、
drop、重建，中断时间比故障本身长得多；而且它会**丢掉故障期间写入的真实数据**。
在有真实用户之后，这是比故障更糟的结果。

**3. 蓝绿部署 / 两套数据库。** 单主机 4 GB 上跑两套 Postgres 不现实。
留给 §9.3 扩容路径的第二步之后。

**4. 把 `vault_sealed` 判成成功（job 绿）。** 理由会是「部署本身确实成功了」。
输在 staging 此刻是不可用的，而一条绿色的流水线会让人以为它可用 ——
下一个人会基于「staging 是好的」去排查别的问题。宁可红着，只要错误信息说清楚
红的原因不是这次部署。

**5. 直接把 T-406 的备份体系提前到 T-012。** 那是 pgBackRest / wal-g + age +
Storage Box + 一次真实恢复演练，明显超出这张卡的 2 人日，而且恢复演练是
§13.8 的不可裁剪项，塞进来只会两件事都做不好。选择是：做一个**明确标注了边界**
的最小护栏，并把「生产启用前必须替换」写进三个地方。
