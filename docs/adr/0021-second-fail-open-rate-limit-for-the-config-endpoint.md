# 0021. fail-open 的第二个例外：`GET /v1/config` 的按 IP 限流

- **Status**: Accepted
- **Date**: 2026-09-10
- **Deciders**: 后端负责人
- **规格引用**: §3.10、§6.2、§7.4、§7.5、§9.2、§14.2
- **取代**: [ADR-0005](0005-rate-limiting-topology.md) 的**决定 3** 中「唯一的例外」这一**限定**。
  ADR-0005 的其余五个决定（自研 Lua 滑动窗口、限流默认 fail-closed、多维度全过才扣、
  §7.5 的两条「总计」不进 Redis、`LimitEnforcer` 的位置）**全部不受影响**，
  `on_store_failure` 的默认值仍然是 `deny`
- **影响**：T-112（本 ADR 随其落地）、T-158（按 **429** 退避；Redis 故障时本端点是 200 而不是 503，
  别把 503 也当成限流）

## Context

T-112 交付了 `GET /v1/config`（强制升级基线 + 维护公告 + feature flag，§3.10 / §6.2 / §9.2）。
它合入时**没有任何限流**，而这不满足 `docs/tasks/README.md` 的 Definition of Done
（原话：「（若涉及新端点）配置限流」）。当时记在 M1 落地记录里的理由是
「§7.5 的速率表里没有它，先改 §7.5」—— 本 ADR 与那次补配一起落地。

这个端点有三个与众不同的性质，它们合起来决定了降级方向：

1. **免鉴权**，所以 IP 是唯一可用的限流主体（§7.5 其余策略的 email_hash / user /
   session / device 都要先认证或先解析请求体）。
2. **客户端每次冷启动都拉一次**。它是 §3.10 强制升级墙的信号源：T-158 的逻辑是
   「启动时调本端点 → `426 client_too_old` → 弹全屏升级墙」。
3. **全仓库唯一刻意不依赖 PG / Redis / Vault、且可缓存的端点**
   （`AbstractApiController::json(noStore: false)` 的唯一调用者，§7.4 的 `no-store`
   默认值在此例外 —— 它不含任何个人数据）。

第 3 条与「给它配限流」之间有一个直接冲突：限流本身要走 Redis。一条 fail-closed 的
策略会把这个端点的可用性绑在 §14.2 那个**单容器、无 AOF** 的 Redis 上 —— 也就是
给一个刻意无依赖的端点新增一个依赖，而且是栈里最脆弱的那一个。

而 ADR-0005 的决定 3 的标题写的是「**唯一**的例外」，
`RateLimitPolicyCoverageTest::testOnlyTheGenericWriteLimiterFailsOpen` 把那个「唯一」
断言成了代码里的不变量（期望值逐字是 `['write_endpoints']`）。
`docs/adr/README.md` 第 4 条又规定「ADR 只增不改」。所以这件事必须走一篇新 ADR。

## Decision

### 1. `config_ip` 标 `on_store_failure: allow` —— 判据没变，变的只是枚举

ADR-0005 的决定 3 给例外定的判据是：

> §7.5 的「全部写接口 | user | 300/min」是纯**防 DoS**，不是安全控制：它挡的是
> 「一个客户端把写接口打爆」，不是「攻击者枚举 username / 轰炸 OTP」。

`config_ip` 落在同一个判据里，逐条对照：

- **没有可枚举的东西。** 响应对所有调用者**同值**（`min_supported_client` /
  `latest_client` / `maintenance` / `feature_flags` 全是部署配置），也不含任何个人数据 ——
  这正是它能被缓存的原因。打一万次和打一次得到的信息量相同。
- **不发信。** 没有 §7.2 T11 那种「用我们的域名给别人的收件箱发信」的滥用面。
- **不碰任何密钥，也不碰数据库。** 它读容器参数 + 时钟，再 `json_encode`。
- 所以对它 fail-open **不会关掉任何防线** —— 故障期间放松的只是「单个 IP 每分钟能做
  多少次 Symfony 内核启动」。

**所以这不是推翻 ADR-0005 的原则，是它的第二个实例。** 被放宽的只有那句「唯一」。

### 2. 为什么这一条尤其该 fail-open，而不只是「可以」

fail-closed 的后果是具体的，不是理论上的：Redis 一挂 → 每次冷启动的 `/v1/config`
都是 `503` → 客户端问不出「要不要弹升级墙」「有没有维护公告」。

这正是 [ADR-0003](0003-problem-details-and-idempotency-semantics.md) 为幂等**否决**掉的
那个后果（§9.2 的 99.5% 可用性在 30 天里只有 3.6 小时预算），也是 ADR-0005 自己给
`write_endpoints` 开例外时用的同一条论证。

还有一层讽刺要写下来：**维护窗口里 Redis 本来就可能在重启**，而这个端点恰好是
用来公告维护的。公告发生在窗口前 24 小时（那时 Redis 是好的），所以这不是致命缺陷 ——
但它说明把这个端点的可用性与 Redis 绑在一起方向就是反的。

### 3. 例外仍然是**封闭集合**，不是「默认可以放松」

`testOnlyTheGenericWriteLimiterFailsOpen` 改名成
`testOnlyTheTwoDocumentedDosPoliciesFailOpen`，期望值从 `['write_endpoints']`
改成 `['config_ip', 'write_endpoints']` —— **两名白名单，不是「随便几条」**。

原来那条断言的 docblock 里那句警告一个字不改地保留：

> fail-open 是一个诱人的「让测试变绿」的旋钮。多标一条就等于悄悄关掉一条安全防线，
> 而症状只在 Redis 故障期间出现 —— 那时没有人在看测试。

第三条要再走一次本 ADR 这个流程。`on_store_failure` 省略时仍然是 `deny`。

### 4. 配额取 IP 300/min —— 约束是 CGNAT，不是攻击者

与 §7.5 其余三条 IP 策略（20/h、60/h、100/h）刻意不同形：那几条守登录与枚举，
真实用户一天碰几次；本端点每次冷启动都被打。

德国移动运营商一个公网 IPv4 背后可能有上千订户共用这一个桶。按 §9.3 的 7500 DAU、
峰值集中 17:00–19:00 估，单个运营商出口的峰值在几十/min 量级 —— 300/min 留约 14 倍
余量，同时仍然挡住单机洪水（那是每秒上千）。

配紧的代价是不对称的：**配松了只是少挡一点廉价流量；配紧了是一整个运营商出口在晚高峰
拿不到配置，升级墙与维护横幅一起失灵，而日志里看起来完全像「限流生效了」。**

## Consequences

### 正面

- T-112 满足 DoD；`/v1/config` 不再是唯一一个没有任何应用层配额的 `/v1` 端点。
- 这个端点的可用性仍然与 Redis 解耦 —— 它继续是那个「在别的东西都挂了的时候还能回答」
  的端点，而客户端正是靠它决定弹不弹升级墙。
- §7.5 的速率表多了一行「降级方向」的说明，把「默认 fail-closed、例外恰好两条、
  判据是什么」写在了规格里，而不是只活在两篇 ADR 和一条测试期望值里。

### 负面（必须写下来）

- **ADR-0005 的标题与决定 3 的小标题从此各有一处不准**（「只对通用写限流开一个
  allow 例外」/「唯一的例外」）。`docs/adr/README.md` 第 4 条规定 ADR 只增不改，
  所以**不改它们** —— 读者要靠 `docs/adr/README.md` 索引行上的加注找到本篇。
  形状与 ADR-0012 决定 1 被 ADR-0013 取代时完全一致。
- **例外从一条变两条，这个方向本身有风险。** 两条的白名单比一条更容易变成三条，
  而「判据」是一句自然语言、不是可执行的判定。缓解手段只有那条封闭集合断言
  与本流程的摩擦，没有更硬的东西。
- **配额只对格式正确的请求生效。** `ClientVersionListener`(40) 与路由都排在控制器
  之前，所以缺 `X-Client` 的 400 与过旧客户端的 426 都不烧配额 —— 也就是说最廉价的
  那种洪水（不带 header）绕过了这条配额。这是既有房规（`RateLimitListener` 的注释：
  「一个即将因缺 `X-Client` 而 400 的请求不该烧配额」），本 ADR 不改它；
  真要挡那一类流量，那是边缘层的事，而 `infra/caddy/Caddyfile` **今天没有任何
  限流或连接数限制**。这一条留给后续的基础设施卡。

## Alternatives considered

### A. fail-closed（`deny`，即默认值）

不动 ADR-0005、不动那条断言、不写本篇 —— 成本最低，而且保住了「例外恰好一条」这个
被测试钉死的不变量（它存在的目的正是防止例外累积）。

否决理由：它把一个刻意无依赖、可缓存、且是客户端唯一配置来源的端点，绑在了栈里最脆弱
的组件上。Redis 一挂，每次冷启动 503。而换来的「安全收益」是零 —— 按决定 1 的逐条对照，
这条策略不保护任何边界。为一个零收益换一个真实的可用性损失，方向是反的。

### B. 不配限流，改为在 Caddy 做边缘限流

理论上更对：最廉价的洪水（不带 `X-Client`）本来就只有边缘层挡得住，而且边缘限流不消耗
应用层资源。

否决理由：`infra/caddy/Caddyfile` 今天没有任何限流指令，Caddy 的 `rate_limit` 需要引入
一个社区插件（也就是改镜像构建），而 §7.5 的表、`RateLimitPolicyCoverageTest` 与 DoD
说的都是**应用层**配额。把这张卡变成一次基础设施改造会把范围放大数倍，而收益是挡住一种
目前没有证据正在发生的流量。两者**不互斥** —— 边缘限流仍然是正确的后续工作，
负面一节把它记了下来。

### C. 做成一条声明式的「按路由绑策略」机制（扩展 `RateLimitListener`）

把 §7.5 的读接口策略都变成路由上的属性，由监听器统一消费。

否决理由：`RateLimitListener` 的注释已经论证过为什么不这么做 —— 读接口各自的维度
（email_hash、challenge_id、session、device）要等请求体解析或认证之后才知道，硬塞进
`kernel.request` 就要在 Shared 内核里解析请求体、调 Vault 算 hash。为一个端点发明这套
机制，代价是改一个优先级被 `ListenerOrderTest` 钉死、且所有 `/v1` 写请求都经过的监听器。
等到第三、第四个读端点需要限流时再来重新评估。
