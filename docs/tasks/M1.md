## T-101 Identity 数据模型与迁移

**预估** 1.5 人日 · **依赖** T-005

**交付物** `users` / `otp_challenges` / `devices` / `sessions` 四张表的 Doctrine 实体、仓储接口与迁移（DDL 见 §17.1）。

**实现要点**
- `users` **不存明文邮箱列**：`email_hash BYTEA UNIQUE`（HMAC-SHA256 + Vault pepper）用于查找，`email_encrypted TEXT`（Vault Transit）用于发信。
- `users.username TEXT UNIQUE NULL`——**可空是有意的**（首次 OTP 验证即建行，此时尚未设 username），不是遗漏。
- `otp_challenges.is_decoy BOOLEAN`：邮箱不存在时创建的哑挑战。
- `sessions.previous_token_hash` 为轮换重放检测预留。
- 所有表带 `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`；外键显式命名 `fk_<table>_<column>`。

**验收标准** 迁移 `up`/`down` 往返通过；`doctrine:schema:validate` 通过；集成测试断言 `email_hash` 唯一约束与 `username` 唯一（大小写不敏感，存归一化小写值）。

**规格引用** §5.2、§17.1

> ✅ **已交付，三条验收标准全部实测通过**（2026-09-05）。
> `composer migration:check` 三步全绿（up → down 往返 → `schema:validate`
> "The database schema is in sync with the mapping files"）；
> `doctrine:schema:update --dump-sql` 报 "Nothing to update"，即映射与迁移逐字一致。
> `composer qa` 1259 tests / 6588 assertions 全绿，集成用例 **0 skip**；
> 覆盖率整体 89.0%、`Module/Identity/Domain` 95.3%（门槛 85%）。
>
> **落地时冒出来的三条约束，合起来决定了全部实现形态**，详见
> [ADR-0011](../adr/0011-doctrine-orm-xml-mapping-and-module-owned-foreign-keys.md)：
> ① deptrac 的 `Identity.Domain: [Shared.Domain]` 让属性映射结构性不可行 → 映射是 XML；
> ② Doctrine 懒加载要继承实体并回填属性 → 实体不能 `final`、属性不能 `readonly`
> （这破了本仓库 `final readonly` 的惯例，是有据可查的例外）；
> ③ `schema:validate` 会把库里的外键与 ORM 元数据对账 → 外键必须建成 `<many-to-one>`，
> 而且索引、唯一约束与每个 `DEFAULT` 都要在 XML 里与迁移**逐字**重复一遍。
>
> **相对任务卡的三处增补**（都不是范围蔓延，理由随代码注释）：
> - 新增 `Shared\Domain\Crypto\HashDigest` + `HashDigestType` / `CiphertextType`
>   两个 DBAL 类型。六个 `BYTEA` 列若用裸 `string`，「hex 写进摘要列」与
>   「用 `===` 比摘要」都拦不住，而后者是 §7.1 明令要常量时间的地方。

> - §17.1 补上了 `otp_challenges` / `devices` / `sessions` 的 DDL 片段

## T-103 `POST /auth/otp/request`

**预估** 1.5 人日 · **依赖** T-101, T-102, T-006

**交付物** 端点实现 → **恒定** `202 {challenge_id, expires_at, resend_after_seconds: 60}`。

**实现要点（防枚举，逐条都是 MUST）**
- 邮箱**不存在**时同样创建 challenge（`is_decoy = true`）并返回一个哑 `challenge_id`，**不发信**；响应体与**耗时**与真实路径不可区分。
- 限流三维：email_hash 1/min、5/h、10/day；IP 20/h；全局熔断。
- 6 位码用 `random_int`（CSPRNG），存 `HMAC-SHA256(code, pepper)`，**不存明文**。
- 新建 challenge 时作废该 email 的旧 challenge（单次登录只允许一个活跃 challenge）。
- 有效期 10 分钟；`attempts` 上限 5。

**验收标准** 集成测试断言：已注册 vs 未注册邮箱的响应体结构、状态码、耗时分布不可区分；限流触发时返回 429 + `Retry-After`。

**规格引用** §3.8、§6.2、§6.3.1、§7.1、§7.5

> ✅ **已交付，两条验收标准都实测通过**（2026-09-06）。
> 容器内 `1394 tests / 7100 assertions` 全绿、**0 skip**；裸机 `composer test`
> 同样全绿（164 skip，都是依赖 compose 栈的既有用例）。

## T-104 `POST /auth/otp/verify` + 注册 + JWT 签发

**预估** 2 人日 · **依赖** T-103

**交付物** 验证端点 → `200 {access_token, expires_in, refresh_token, user}`；首次验证成功即创建 `users` 行（注册）。

**实现要点**
- `hash_equals()` **常量时间**比较；`attempts++`，> 5 或过期 → 401；decoy → **恒 401 且耗时与真实路径相同**。
- 成功后：upsert user → 创建 `device`（客户端生成 id，安装级唯一）+ `session` → 签发 JWT（EdDSA Ed25519，claims `sub, sid, did, jti, iat, exp`，**15 分钟**）+ refresh（32 字节随机，Base64url，不透明，**90 天滑动**）→ 写 `audit_log(login_success)`。
- 新设备登录 → 向该用户所有既有设备发推送 + 向邮箱发提醒信（设备型号、大致时间、粗粒度地区）+ 信中"这不是我"的一键撤销链接（**同样走 POST 确认**）。
- `POST /auth/otp/verify` 限流：challenge_id 5 次总计；IP 60/h。

**验收标准** 单测覆盖常量时间比较与 decoy 路径；集成测试断言首次验证创建的 user 行 `username IS NULL`。

**规格引用** §6.3.1、§7.1、§7.5

> ✅ **已交付，两条验收标准都实测通过**（2026-09-06）。
> 容器内 `1543 tests / 7638 assertions` 全绿、**0 skip**；PHPStan level 8 无错，
> `deptrac` 0 violation / 0 uncovered、selftest 四个场景全过，
> `schema:validate` 与迁移 up/down 往返全绿，Spectral 0 warning。
> 覆盖率 `Module/Identity/Application` **97.6%**、`Module/Identity/Domain` 92.8%、
> `Shared/Domain` 98.6%、整体 91.3%（门槛 85 / 85 / 70）。
>
> `verifyOtp` 的**契约一个字没改** —— 它早在 T-007 就写好了。改的是 `requestOtp`
> 的 description（见下）。
>
> ### ⚠️ 开工第一天发现的事：**这个系统当时没有任何注册路径**
>
> T-103 交付的行为是「未注册邮箱 → decoy challenge + **不发信**」，
> 而 §5.2 / §6.3.1 / 契约三处都写着「首次验证成功即注册」，且没有 signup 端点。
> 两者放在一起就是：新用户永远收不到码 → 永远走不到 verify → **永远无法注册**。
> M1 的出口条件在第一步就走不通。
>
> 它没有在任何用例里显形：既有用例要么只测 request（那里没有注册的概念），
> 要么自己往库里塞一个 user 再断言。教训写在 T-103 的更正块里 ——
> 「两条路径不可区分」被测得很细，而「这两条路径合起来能不能完成产品流程」没人测。
>
> 修复是 [ADR-0014](../adr/0014-otp-always-sends-a-code.md)：**对任意邮箱都真发码**。
> `RequestOtpService` 因此**不再注入 `UserRepositoryInterface`** ——
> 防枚举从「配平两条路径的做功」升级成「服务端在那条路径上根本没查」，
> 更强，也不再需要人肉维护。连带删掉了 T-103 那行「返回值被丢弃的 `encrypt()`」。
>
> 代价是明知并接受的，写在 ADR 的 Consequences 里：§3.1 那句「用户无法让系统向
> 任意第三方邮箱发信」不再成立，准确表述变成「只能向任意邮箱发一封 OTP，
> 每邮箱每天 10 封封顶」。§7.5 的三个窗口一个都没放宽。
>
> ### 攻击面搬到了 verify，那才是本任务真正的难点
>
> ADR-0014 之后，攻击者能对任意邮箱拿到一个**真实的** `challenge_id`
> （信进了受害者的收件箱，他看不到），再用错码来问「这个邮箱注册过吗」。
> 要挡的是这一对：
>
> - 「**未注册**邮箱的 challenge + 错码 → 401」
> - 「**已注册**邮箱的 challenge + 错码 → 401」
>
> 好消息是这两条在 `VerifyOtpService` 里**根本不是两条**：拒绝路径不查 `users`、
> 不加密、不发信，做的事只有 `hmac(code)` ×1 + `findById` + `attempts` 的 UPDATE。
> 三处强制点：
> - `VerifyOtpServiceTest::testEveryRejectionShapeDoesTheSameAmountOfWork()` ——
>   六种拒绝形状（码错 / 过期 / 已消费 / 次数耗尽 / 不存在的 id / 遗留哑挑战）
>   的往返账单逐项相等。
> - **那条布尔链的次序是安全约束**：`hash_equals` 永远执行，`isDecoy()` 永远排在它后面。
>   反过来写会让哑挑战少一次 Vault HMAC，而「是哑挑战」恰好等价于
>   「这个邮箱在上个版本里没注册过」。`testADecoyIsRejectedEvenWhenTheCodeHashMatches()` 钉它。
> - `OtpEnumerationResistanceTest` 新增的 verify 三层断言（形状 / 库层足迹 / 墙钟中位数）。
>
> ### 相对任务卡的三处偏差（都不是范围蔓延）
>
> - **`audit_log(login_success)` 没写。** 那张表归 T-401（M4），本任务不提前建。
>   替代是 `login_total{result=registered|success|rejected}` 计数器
>   （与 T-103 的 `otp_request_total` 同形）。交接：审计落点在 `VerifyOtpService`
>   事务提交之后那一行。
> - **新设备登录只发信，不发推送。** FCM 整条链路归 T-306（M3），
>   它还需要 `push_token` 的下发（T-105）与一个尚不存在的推送 Port。
>   邮件是两条渠道里更重要的那条 —— §7.2 T02 的缓解就落在这封信上，
>   而推送发到的正是可能已被控制的那些设备。
> - **「这不是我」链接指向设备管理落地页**（`{APP_PUBLIC_BASE_URL}/l/devices`），
>   不是带令牌的一次性撤销 URL。后者需要 T-105 的撤销端点与令牌存储。
>   同理 `approximate_region` 没有 GeoIP 可用，填的是本地化的「Unbekannt / Unknown」——
>   **不编一个假地区**：模板正文写着「Region 是粗略估计」，填假值会把那句话变成谎话，
>   而这封信的全部价值在于可信。
>
> ### 落地时踩到、值得记住的五个坑
>
> - **PHP 的 OpenSSL 扩展签不了 EdDSA。** `openssl_sign()` 没有对应的 `OPENSSL_ALGO_*`，
>   `openssl_pkey_get_details()` 对 Ed25519 也不给裸密钥字节。能签的是 `ext-sodium`，
>   而它要 32 字节**裸 seed**。好在 Ed25519 的 PKCS#8 编码是**唯一且定长**的
>   （48 字节 = 16 字节固定头 + seed），所以那段转换是定长切片，不需要 ASN.1 解析器。
>   ⚠️ 别把它「泛化」成一个 DER 解析器 —— 那正是 CVE 的产地。
> - **切错位置不会有任何症状。** 把内层 OCTET STRING 的两字节头也算进去，仍然得到
>   32 字节，`sodium` 也照样接受，只是推出来的公钥不同 —— 于是线上签出的每一枚
>   token 谁也验不过，而所有「自己签自己验」的单测全绿。
>   钉它的是两条独立验签：单测用 `sodium_crypto_sign_verify_detached()` 重算一遍，
>   集成测试拿 **Vault 里那份 `public_key`** 验一遍。
> - **`attempts` 必须饱和，不能一直加。** 上限用完之后调用方**仍然要**写库
>   （「次数耗尽」这种拒绝必须与「码错了」做同样多的功），于是这一列会被一条已经
>   死掉的挑战反复写。不封顶的话它是无界的，而它是 SMALLINT ——
>   足够多的源 IP 打同一个 `challenge_id` 能把它顶过 32767，那时 PG 拒绝 UPDATE，
>   于是那条挑战上的每一次请求都变成 **500**。现在 `recordAttempt($max)` 到上限即饱和。
> - **成功路径不能调 `settle()`。** 它必然越过 120 ms 预算（建三张表 + 签 JWT +
>   入队一封信），硬填会让 `MonotonicTimeBudget` 在**每一次正常登录**上打一行
>   "Constant-time budget overrun" —— 而那行是 §3.8 的安全告警，被正常流量淹掉
>   之后就再也没有信号价值了。「200 与 401 耗时不同」本身不是泄漏：走到 200
>   需要先拿到正确的 6 位码。
> - **JWT 密钥读不到要收敛成 503，不能用 `VaultClient` 的默认映射。** 那个映射把
>   4xx（含 404）归 500，对 transit 是对的；但签名密钥读不出来的后果是
>   「所有人都登不进去」，处置永远是一个运维动作，与 ADR-0004 的手工 unseal 同构。
>   500 会让客户端不重试，且把一次可预期的运维窗口报成 §14.4 的「5xx 率高」告警。
>
> ### 手工验证（本地 compose + Mailpit，2026-09-06）

## T-105 Refresh 轮换与重放检测、logout、设备管理

**预估** 2 人日 · **依赖** T-104

**交付物**
- `POST /auth/token/refresh`（轮换后的新令牌对）、`POST /auth/logout`
- `GET /v1/me/devices`（含当前设备标记）、`DELETE /v1/me/devices/{id}`（远程登出）、`PUT /v1/me/devices/{id}/push-token`

**实现要点**
- 每次刷新签发新 refresh token，旧 token **立即失效**，`previous_token_hash` 记录。
- 收到**已使用过的** refresh token → 判定令牌被窃：撤销该会话家族全部令牌 + `audit_log(reuse_detected)` + 告警 + 给用户发安全提醒邮件。
- 服务端**不做** access token 黑名单（15 分钟窗口可接受），但会话撤销后 refresh 立即失效。
- `revoked_reason` 取值：`logout` / `reuse_detected` / `user_revoked` / `account_deleted`。
- 限流：refresh 按 session 60/h。

**验收标准** 集成测试：重放旧 refresh token → 整个会话家族被撤销且发出提醒邮件；远程登出某设备后该设备的 refresh 立即失效。

**规格引用** §5.2、§7.1、§7.5

> ✅ **已交付，两条验收标准都在真栈上实测通过**（2026-09-07）。
> 容器内 `1687 tests / 8327 assertions` 全绿、**0 skip**；覆盖率
> `Module/Identity/Application` 98.3% / `Identity/Domain` 92.8% / 整体 90.8%
> （门禁 85/85/70）。`composer migration:check` 三步全绿 ——
> **本任务不产生迁移**，T-101 的 DDL 已经覆盖全部需求。
>
> ### 两条验收标准的实测形状
>
> - **重放** —— `SessionLifecycleTest::testReplayingAnOldRefreshTokenRevokesTheWholeFamilyAndQueuesTheAlert()`：
>   登录 → 轮换一次 → 拿旧令牌再刷 → 401 + `sessions.revoked_reason = 'reuse_detected'`
>   + 提醒信入队 + **刚签发的那枚新令牌也一起失效**（后者才是「家族」二字的含义）。
>   与它成对的是 `testAReplayedTokenLooksExactlyLikeAnUnknownOne()`：
>   被窃检测**不能**从响应里看出来，否则攻击者就有了一个「我这枚令牌是不是刚被换掉的」
>   的免费预言机。
> - **远程登出** —— `testRemotelyRevokingADeviceInvalidatesItsRefreshTokenImmediately()`：
>   同一账号两台设备，踢掉 B → B 的 refresh 当场 401、A 不受影响、
>   B 的 `push_token` 已清空、B 不再出现在设备列表里。
>
> 手工验证走了一遍真链路（compose 栈 + Mailpit，curl）：
> `otp/request` → 收到真码 → `verify` → `refresh` ×1 → 重放 → 401 +
> 库里 `reuse_detected` + 德语安全提醒信实发；两台设备 → `GET /v1/me/devices`
> （`is_current` 正确、响应体无 `push_token`）→ `PUT .../push-token` 204 →
> `DELETE` 204 → B 的 refresh 401 → `logout` 204 → 无 Bearer 的 logout 401。

> ### ⚠️ 相对任务卡的三处偏差
>
> - **鉴权器从 T-108 提前到本卡，这不是范围蔓延，是依赖顺序错了。**
>   `logout` 与三个 `/me/devices` 都要 Bearer，而仓库里没有任何 access token
>   验签器（没装 security-bundle，`SigningKeyProviderInterface` 只有 `currentKey()`）。
>   文档三处（该接口的类注释、两个 Anonymous 解析器、T-104 的交接清单）都把它写给了
>   T-108 —— 而 T-108 依赖 T-107、T-107 依赖 T-104，排在本卡**之后**。

>   两条「待接入」：§7.5 的「全部写接口 user 300/min」从此真的按 user 生效，
>   幂等键也按 user 隔离（此前全局按 IP —— 两个用户撞同一个键时后者会拿到前者的响应）。

> ### 落地时踩到、值得记住的六个坑
>
> - **⚠️ 免鉴权白名单必须按路由名，不能按路径前缀。** 免鉴权的端点里有三个在
>   `/v1/auth/` 下，于是「前缀一律放行」看起来完全等价 —— 但
>   `POST /v1/auth/logout` **也**在那个前缀下，而它是 auth 组里唯一需要 Bearer 的。
>   写成前缀的后果是任何人都能撤销任何会话，**而所有测试照常绿**（logout 本来就 204）。
>   `AuthenticationCoverageTest` 拿白名单与契约里的 `security: []` 逐条对账。
> - **`revokeAllForDevice()` 不能写成批量 DQL `UPDATE`。** 那会绕过
>   `Session::revoke()`，于是「首个 reason 胜出」失效 —— 一条已因 `reuse_detected`
>   撤销的会话会被远程登出改写成 `user_revoked`，这个账号曾经发生过令牌被窃
>   就再也查不出来。ORM 3 又拿掉了 `clear($entityName)`，身份映射也没有便宜的补救。
>   改成逐行水合 + `revoke()`：一台设备上的会话是个位数量级，付得起。
> - **`findByRefreshTokenHash()` 要加 `PESSIMISTIC_WRITE`。** 轮换是读-改-写，
>   两个并发刷新不加锁会丢失更新 —— 而先提交的那枚新令牌已经发回客户端了，
>   它从此在库里不存在，客户端下次刷新 401 且没有任何日志能解释。
> - **合法客户端的重试会被误判成被窃。** 服务端轮换完、响应在路上丢了，
>   客户端拿旧令牌重试 → 命中 previous → 会话被撤销 + 一封安全警报，
>   而实际上什么都没发生。唯一的缓解是契约给这个端点挂的 `Idempotency-Key`
>   （中间件回放同一对令牌）。**不要**在服务端「宽容一点」——
>   那等于给被窃令牌开一个可用窗口。客户端侧的对应约束是 T-150 的 Mutex 串行化。
> - **`validation_failed` 在本仓库映射到 400，不是 422**（`ErrorCode::httpStatus()`）。
>   422 留给 `username_invalid` / `limit_exceeded` / `idempotency_key_reused`。
>   另外 `{}` 走的是 `malformed_request` 而不是字段校验：`json_decode('{}', true)`
>   给出空 PHP 数组，而 `array_is_list([])` 为 true，于是
>   `AbstractApiController::decodeBody()` 先一步判它「不是 JSON 对象」。
> - **`refresh_replay` 邮件的文案与实现对不上。** T-102 起草它时撤销范围还没实现，
>   草稿写的是「**所有**设备已登出」，而实际范围是一条会话家族（别的设备不受影响）。
>   已改成「一台设备」。这不是措辞偏好：一个两台设备的用户读到「所有设备已登出」、
>   转头发现另一台还登着，从此就不会再认真读这封信 —— 而 §7.2 T02 把它列为
>   「邮箱被接管」唯一能被用户察觉的信号。
>
> ### 留给后续任务的四条

## T-108 onboarding 拦截器与 `/v1/me`

**预估** 1 人日 · **依赖** T-107

**交付物** `username IS NULL` 状态机的全局强制 + `GET /v1/me` + `PATCH /v1/me`（`locale`、通知偏好）。

**实现要点**
- `username IS NULL` 的用户处于 `onboarding_incomplete`：除 `GET /v1/me`、`POST /v1/me/username`、`POST /v1/auth/logout` 外，**所有** `/v1` 端点返回 `403 username_required`。

**验收标准** 参数化测试遍历全部 `/v1` 端点，断言 onboarding 未完成的用户只能访问白名单三个。

## T-109 Wallet：cards 模型与 CRUD

**预估** 2.5 人日 · **依赖** T-005, T-104

**交付物** `cards` 表 + `GET /v1/cards`（游标分页）、`POST /v1/cards`、`GET /v1/cards/{id}`、`PATCH /v1/cards/{id}`、`DELETE /v1/cards/{id}`。

**实现要点**
- **`sort_order` 与 `is_pinned` 不在 `cards` 上**（在 `card_members` 上，见 T-110）。这是共享模型的必然结果，最容易漏掉。
- `barcode_value_encrypted` / `note_encrypted` 走 Vault Transit；列表查询**必须**用 `BatchDecryptor` 一次批量解密（禁止循环调 Vault）。
- `barcode_value_fingerprint BYTEA`：HMAC(payload)，用于重复卡检测，不可逆。
- `encryption_scheme TEXT NOT NULL DEFAULT 'server_v1'`（为二期 E2EE 预留）。
- **创建幂等**：body 含客户端生成的 UUIDv7 `id`；`id` 已存在且属同一用户 → `200` + 现有实体；属他人 → `409 id_conflict`。
- **更新乐观锁**：`If-Match: "<revision>"`；匹配 → `revision += 1` + `200`；不匹配 → `409 {"code":"revision_conflict","current":{…}}`。
- **删除**：软删（`deleted_at`，90 天后硬删）+ 墓碑。
- 权限：`PATCH`/`DELETE` 对**非 owner 一律 `403 insufficient_role`**，即使请求体合法、revision 正确。

**验收标准** 契约测试全绿；集成测试覆盖幂等创建、revision 冲突、批量解密性能基准（200 张卡 bootstrap P95 ≤ 700 ms）。

**规格引用** §5.2、§5.3、§5.4.3、§6.2、§9.1

## T-110 card_members 与 placement 端点

**预估** 1 人日 · **依赖** T-109

**交付物** `card_members` 表 + partial unique index + `PUT /v1/cards/{id}/placement`。

**实现要点**
- 建卡时**同时**写入一行 `card_members(role='owner')`——单人钱包阶段也必须有，否则 M3 的共享要回头补数据。
- ```sql
  CREATE UNIQUE INDEX uq_card_single_owner
    ON card_members (card_id) WHERE role = 'owner' AND left_at IS NULL;
  ```
- `placement`（`sort_order` / `is_pinned`）是**成员私有字段**，**不走 revision 锁**；owner 与 viewer 均可调用——这是 viewer 唯一的写入端点。
- `left_at` 是成员墓碑字段，M3 会重度使用，此处先建好。

**验收标准** 集成测试断言：尝试插入第二行 owner 被索引拒绝；两个成员各自的 placement 互不影响。

**规格引用** §5.2、§6.2

> ### 落地记录（2026-09-09）
>
> `card_members` + `PUT /v1/cards/{id}/placement` 已落地。核心决策进了
> [ADR-0020](../adr/0020-card-members-belongs-to-sharing-and-wallet-reads-it-through-three-ports.md)，
> 这里只记它没覆盖的东西。
>
> ### 这张表归 Sharing，不归 Wallet —— 于是 M1 里立起了第二个模块
>
> 任务卡在 M1、依赖 T-109，读起来像是「往 Wallet 里加一张表」。但 §4.2 的
> 模块图逐字把「卡成员（owner/viewer）」划给 **Sharing**，而 M3 的三张卡
> （T-303 级联撤销、T-304 邀请接受、T-305 成员管理）**全都**在这张表上写。
> 归 Wallet 会让那三张卡反过来经 Wallet 的 Port 写「自己的」表，
> Sharing 变成空壳。
>
> 所以 T-110 实际交付的是 **Sharing 模块的第一批代码**：实体（本仓库第一个
> 复合主键实体）、值对象、仓储、三个端口、两个 DTO、一个服务。
> **1 人日的估算按「加一张表 + 一个端点」算，实际接近 2.5** —— 清单里没有
> 一项超出任务卡的交付物，只是「建一张表」在这个仓库里的真实成本
> （新模块的 `Domain` / `Application` 各要过 85% 覆盖率门槛，外加一篇 ADR）。
>
> ### ⚠️ ADR-0019 的「两条」是错的，实际是三条
>
> 那个计数只有在 `card_members` 归 Wallet 时才成立（那样 `card_id → cards`
> 是模块内部外键）。归 Sharing 之后 `card_id → cards` 也跨模块，
> 而且它是清单里**第一条指向另一个模块业务表**（而不是 `users`）的外键。
> ADR-0019 的「影响」行与 Consequences 已随本卡修订，末尾补了一节「T-110 补记」。
>
> ### 部分索引：ADR-0019 的判断成立，谓词一次就对
>
> `uq_card_single_owner`（`WHERE role = 'owner' AND left_at IS NULL`）原样落地，
> `schema:validate` **第一次就同步**。做法是先建表再拿真值，而不是照着
> `Card.orm.xml` 猜：
>
> ```sql
> SELECT indexdef FROM pg_indexes WHERE tablename = 'card_members';
> ```
>
> PG 规范化后是 `((role = 'owner'::text) AND (left_at IS NULL))`。
> ⚠️ 是 `role` 不是 `(role)::text` —— 那一列是 **TEXT** 不是 VARCHAR，
> 计划阶段猜的就是错的那个形式。抄错的症状是 dump-sql 反复吐 DROP + CREATE。
>
> ⚠️ 顺带确认了一件 ADR-0019 第 3 条容易被误读的事：**三条外键列不需要各补一条
> `<index>` 声明。** 那一条管的只是「迁移里真的建了的索引」；DBAL 给外键列自动
> 补的 `IDX_<hash>` 在 ORM 侧与库侧内省时**都会**生成、同名互相抵消
> （`Table::_addForeignKeyConstraint()` 自己的注释说明了后者）。
> 所以 XML 里只声明了 `uq_card_single_owner` 与 `idx_card_members_user` 两条。
>
> ### 三个窄端口，而不是一个胖端口
>
> `CardOwnershipRegistrarInterface` / `CardMembershipReaderInterface` /
> `CardPlacementWriterInterface`，由**一个类**实现。合并的诱惑很大（三个方法、
> 同一张表），但它们的**前置条件互相矛盾**：registrar 必须在事务内
> （`isInTransaction()` 断言 + 抛 `\LogicException`），reader 绝不该在，
> writer 两者都不要求。而且 reader 要注进 `CardViewAssembler` ——
> 那个类不该拿到 `registerOwner()` 这种写能力。口径同 Notification 的三个端口。
>
> ### placement 端点留在 `Wallet.Http`，判据是 `CardBody`
>
> 「写的是 Sharing 的表，端点也该归 Sharing」这个直觉由端口满足即可。
> 真放过去要克隆两个类：`CardView`（装**明文码值**，它「只能由
> `CardViewAssembler` 构造」的不变量当场作废）与 `CardBody`
> —— 而后者的类注释写着它存在的全部理由就是「组装代码有第二份的话，
> 加字段时必然漏一处，且漏掉的那个端点的契约测试照样是绿的」。
> **T-110 正是给 `Card` 加两个字段的那次提交**，五个既有端点一行没改，
> 那句注释第一次被兑现。
>
> ### ⚠️ 留下一处「两个真相来源」，收口在 T-305
>
> 角色来自 `card_members`（assembler），可见性仍来自 `Card::isOwnedBy()`
> （`CardQueryService::get()`）。M1 里恰好一致只因为没有 viewer。
> 于是出现一个真实的不对称：**viewer 能 `PUT …/placement`，却不能 `GET` 同一张卡。**
>
> 落地时这一条把 `CardPlacementEndpointTest` 里那条「两个成员各自 placement
> 互不影响」用例弄红过一次（viewer 侧 `GET` 返回 403，读回来是 null）。
> 处理方式不是去改 placement，而是：用例改成读 `PUT` 的 200 响应体
> （那本来就是「调用者视角的卡」），并**新增一条把已知的错断言下来**的用例
> `testAViewerStillCannotGetTheCardUntilT305()`。T-305 落地时它会红 ——
> 那时该改的是它，不是回头改 placement。修法写在 `CardQueryService` 的类注释里：
> 把检查**挪到**成员表上，而不是再加一次查询。
>
> ### 相对任务卡的三处增补
>
> - **迁移带数据回填，且刻意包含软删的卡。** 不回填的话 T-109 期间建的每张卡
>   都变成「没有成员行的孤儿」。含软删是因为 `DELETE` 只写 `deleted_at`、
>   那个 id 仍被占用，而建卡的幂等重放会把它原样返回。目标是让
>   `cards → card_members` 是**全函数**，于是「卡有、owner 行没有」从一种状态
>   降级成一个 bug —— `CardViewAssembler::assertComplete()` 直接抛（500 + 日志），
>   不回退到任何默认角色（三条备选都更糟，写在那个方法的注释里）。

>   `{"sort_order": 9223372036854775807}` 是一个**合法的 JSON 整数**，
>   `is_int()` 收得下，然后在 flush 时变成一个 **500** —— 而契约写的是 400。
>   一个字段级校验漏掉就直接送 500 的洞，朴素实现一定会踩。
>   `CardFields::requiredInt32()` + `out_of_range`。
> - **`CardMember::leave()`。** 任务卡说「`left_at` 此处先建好」，而只建列不建

> `left_at`，因为 §5.2 要求卡墓碑的 audience 取**删除前**的成员快照。
> 这一条写进了迁移文件头与 `DeleteCardService` 的类注释，免得 T-201 有人来「修」它。

**预估** 0.5 人日 · **依赖** T-004

> ### 任务卡没提、但必须先想清楚的一件事：本端点自己也会 426

> ### `maintenance` 的四个决定
>
> 任务卡给的是三个字段和一句「提前 24 小时下发」，落地时要补的决定有四个：
>
> | 决定 | 选了什么 | 为什么 |
> |---|---|---|
> | 状态来源 | `MAINTENANCE_WINDOW_START` / `_END` 两个 env，三个字段全部由 `MaintenanceWindow::statusAt()` 按 `ClockInterface` 派生 | 直接把三个字段做成 env 的话，运维要手算并维护它们的一致性：开始时翻 `active`、同时维护一个递减的 `retry_after`、结束后三个一起清。那是三次人工编辑，而**漏掉最后一次的后果是横幅永远挂着**。只配两头则只有「填进去」和「过期后清掉」两步，而且不清也无害 |
> | 为什么不是 Redis | 本栈 Redis 单容器、无 AOF，§8.2 的定位是「限流计数保留 24 小时」 | 一次重启就把公告吃掉；而且 `/v1/config` 必须在 Redis 不可达时照样回答，那要再写一条降级路径，而「降级到没有公告」与「公告丢了」在外部看来一模一样 |
> | `retry_after` 语义 | **仅 `active` 为 true 时有值**（到窗口结束的秒数），否则 `null` | 它是 §6.1 里 503 那个 `Retry-After` 的同义物，「多久以后可以重试」对一个还没开始的窗口没有意义。提前公告只靠 `message_key` —— 而这够了：§9.2 把窗口**固定**成每周二 03:00–04:00 CET，客户端的德语文案里本来就能写死时间。这也解释了规格为什么只给三个字段、没给时间戳 |
> | `feature_flags` | 恒 `{}` | M1 没有任何消费者。照 T-108 拒绝为「通知偏好」发明模型的先例；§13.6 允许后续作为可选字段新增 |
>
> ⚠️ **offset 必填**，`2026-09-15T03:00:00` 这种写法直接 500。不带 offset 的值会按容器
> `date.timezone` 解释，于是**同一份配置在两个环境指向不同时刻** —— 而本地与 CI 通常都是
> UTC，于是这个故障只在生产显形，症状是「横幅早了/晚了两小时」，没人会把它和时区联系
> 起来。德国是 CET/CEST 两个 offset，夏令时切换当天还会再错一小时。
>
> ⚠️ **只配一头也直接 500**，不宽容地当成「无窗口」：漏填 `END` 的那次部署，运维以为
> 公告发出去了而客户端什么也没收到，这件事要等到维护窗口当天有用户投诉才会被发现。
>
> ### 顺带补掉的一个既有洞：生产的升级基线此前改不动

> `docker-compose.prod.yml` 把 app 的 `volumes: !reset null`、`Dockerfile` 的 prod target
> 直接 `COPY . .`，于是生产读的是**烤进镜像的** `backend/.env`（放行一切的
> `android/0.0.0 (1)`）。那时无人可见所以无害 —— 而 `GET /v1/config` 一上线就开始把它
> **对外宣告**成强制升级基线，也就是说抬高基线这个纯运维动作需要重新构建并推送一个镜像。
>
> 三处配置面一起补上了：`docker-compose.base.yml` 的 app `environment`、

>
> ### ⚠️ 爆炸半径与 `ClientVersionListener` **不一样** —— 实测后改了注释
>
> 落地时照 T-004 的先例写了「配错 → 500 → 健康检查把这台机器挡在流量之外」，
> 实测发现**后半句不成立**，三处注释已改正：
>
> - `ClientVersionListener` 挂在 `kernel.request` 上，`EventDispatcher::sortListeners()`
>   会在调用任何监听器之前实例化它 → `MIN` 配坏让**每个**请求 500（含 `/health/*`），
>   compose healthcheck 与 §14.3 的部署当场失败；
> - `ClientConfigProvider` 是**控制器的依赖**，只在 `/v1/config` 被打到时构造 →
>   `LATEST` 或窗口配坏**只有** `/v1/config` 500，`/health/ready` 实测照样 200，
>   Ansible 的健康门禁不会拦住这次部署。唯一的安全网是 §14.4 的 5xx 告警。
>
> 这是**刻意接受**的：把 provider 做成一项 `HealthCheckInterface` 就能让 ready 变红，
> 但那意味着**一个维护公告的时间戳打错字会让整个 API 下线**。对一个纯咨询性的字段，
> 降级成「公告发不出去」是对的取舍 —— `/health/ready` 的职责是基础设施依赖，不是配置审校。
>
> ### 全仓库唯一一处可缓存的 `/v1` 响应，而那个 `Vary` 是承重的
>
> `AbstractApiController::json()` 的 `$noStore` 参数注释从 T-004 起就写着「T-112 的
> `/v1/config` 是唯一预期的例外」。本卡是它的第一个（也是目前唯一的）调用者：
> `public, max-age=60`。

> 喂给旧客户端 —— **强制升级墙就再也不出现了，而且没有任何错误可查**。
> 426 那一侧不用操心：`ApiProblemFactory` 给所有 problem 响应都打了 `no-store`。

>   上千订户共用这一个桶。按 §9.3 的 7500 DAU、峰值集中 17:00–19:00 估，单个运营商出口的
>   峰值在几十/min 量级，300/min 约 14 倍余量，同时仍然挡住单机洪水（那是每秒上千）。
>   代价不对称：配松了只是少挡一点廉价流量；**配紧了是一整个运营商出口在晚高峰拿不到配置，
>   升级墙与维护横幅一起失灵，而日志里看起来完全像「限流生效了」。**
>
> **fail-open 要动一篇 Accepted 的 ADR，这是本次最重的那部分。** ADR-0005 的标题与决定 3
> 都写着「只对通用写限流开一个 allow 例外」，而 `testOnlyTheGenericWriteLimiterFailsOpen`
> 把那个「唯一」断言成了代码里的不变量。`docs/adr/README.md` 第 4 条规定 **ADR 只增不改**，
> 所以不能去改它 —— 照 ADR-0013 取代 ADR-0012 决定 1 的先例新写了
> **ADR-0021**：新 ADR 头部加 `取代:` 字段逐字写明取代的是哪一条、其余不受影响；
> **不动旧文件**；只在 `docs/adr/README.md` 的索引行上加注。
>
> 判据没变 —— ADR-0005 给例外定的是「纯防 DoS，不是安全控制」，而 `config_ip` 逐条符合：
> 响应对所有调用者同值（没有可枚举的东西）、不发信、不碰任何密钥、不碰数据库。
> 变的只有那句「唯一」，而白名单仍然是**封闭的两条**
> （`testOnlyTheTwoDocumentedDosPoliciesFailOpen`，加第三条要再走一次这个流程）。
>
> 而这一条尤其该 fail-open：`/v1/config` 是全仓库唯一刻意不依赖 PG / Redis / Vault、
> 且可缓存的端点。fail-closed 等于给它新增一个 Redis 依赖 —— Redis 一挂，每次冷启动都 503，
> 客户端连「要不要弹升级墙」都问不出来。讽刺的是**维护窗口里 Redis 本来就可能在重启**，
> 而这个端点恰好是用来公告维护的。
>
> **消费点在控制器里，不是监听器。** `RateLimitListener` 的 `WRITE_METHODS` 刻意不含 `GET`，
> 它的注释原话：「§7.5 对读接口的限流是按端点配的，在这里一刀切会与那些更严格的策略叠加成
> 一个说不清的复合限额」。最接近的结构先例是 `ProbeApiController`（GET、免鉴权、控制器里直接
> `consume()`）。`ClientConfigProvider` 保持纯粹，不碰限流。
>
> ⚠️ **配额只对格式正确的请求生效**，这是既有房规不是新洞：`ClientVersionListener`(40) 与
> 路由都排在控制器之前，所以缺 `X-Client` 的 400 与过旧客户端的 426 都不烧配额。两条用例
> 钉着它，而它们真正防的是「有人把 `consume()` 挪进一个排在 40 之前的监听器」——
> 那会让一个被升级墙挡住的旧客户端把整个出口 IP 的配额烧光，**同一个出口后面的新客户端
> 跟着一起 429**。CGNAT 下这是最坏的那种耦合。
>
> 契约侧**一个字节都没改状态码**：`/config` 从第一版起就声明了 `'429': TooManyRequests`，
> 而那个组件已经带上 `Retry-After` 与 `X-RateLimit-Remaining`。只在 description 里补了
> 配额与「限流器不可用时仍然 200，不是 503」——后者是给 T-158 的，它的退避只该按 429 写。
> 顺带：那个 `'429'` 在本次之前**从来没有被任何真实响应校验过**，现在有了。
>
> **四条新用例 + 六条变异验证**（明细见 PR）。
>
> ⚠️ 第七条变异没做出来，记在这里免得下一个人重试：原本想用「把
> `ClientVersionListener::PRIORITY` 从 40 降到 4」来证明「426 不烧配额」那两条用例
> 不是空转。**它不红** —— 因为控制器在**所有** `kernel.request` 监听器之后才跑，
> 一个监听器抛异常时控制器根本不会被调用，与优先级无关。所以那两条用例守的不是
> 优先级，是**结构**：只有把 `consume()` 整个挪进一个监听器才会让它们红，
> 而那不是一行能改出来的。用例的注释写的就是这个失败模式。
>
> 不加「真的打 301 次」的集成用例：
> 滑动窗口本身由 `tests/Api/RateLimitTest` 打真 Redis 验（`PROBE_LIMIT=3` 正是为了不在
> 测试里发几百个请求），重复它只会让套件变慢。
>
> ### 刻意没做的两件事
>
> - **不做服务端维护模式开关。** §9.2 的 `maintenance` 是 200 响应里的咨询性元数据，
>   不是拦流量的闸；窗口里真正的 503 来自 Caddy / 停机本身。没碰
>   `ApiProblemExceptionListener` 与 503 机制。
> - **不动 `OnboardingListener::EXEMPT_ROUTES`。** 它只在请求带着 `AuthContext` 时才判定，
>   而公开路由永远不带 —— 结构上就在它之外，`OnboardingCoverageTest` 的
>   `protectedProductApiRoutes()` 也会自动把它排除。
>
> ### 顺手改掉的一处过时注释
>
> `config/services.yaml` 与 `ProbeApiController` 都写着「第一个真实端点 `/v1/config`
> 属 T-112」。那是 T-004 当时的判断，早就不成立了：auth（T-103/104）、me（T-108）、
> cards（T-109/110）都先于本卡落地，`debug:router` 里已经有 18 条 `/v1` 路由。
> 改成了事实陈述，并说明夹具为什么仍然留着（横切层的契约测试不该依赖任何真实端点的
> 业务前提）。本卡真正的「第一」是：`Shared\Http` 下的第一个产品端点。
>
> ### 交给 T-158 的四件事
>
> - **升级墙的信号是 `GET /v1/config` 的 426**，不是把 `min_supported_client` 拿回本地比较。
>   本地比较在「客户端时钟/版本号读取有误」时会与服务端不一致，而 426 是服务端的判定本身。
> - **`retry_after` 只在 `active` 为 true 时有值**，公告期是 `null`。横幅要显示的时间
>   写在德语文案里（§9.2 固定每周二 03:00–04:00 CET），服务端不下发时间戳。
> - **`message_key` 两个取值**：`maintenance.scheduled`（24 小时内将开始）/
>   `maintenance.in_progress`。生成出来的 Kotlin 枚举带一个
>   `unknown_default_open_api` 兜底分支，§13.6 将来新增取值时老客户端落在那里 ——
>   **不要**把它当错误处理，当「没有公告」处理。
> - **维护期间离线读卡不受影响**，横幅文案要体现这一点（任务卡原话），这是离线优先架构的额外收益。

## T-113 Scheduler 与清理任务

**预估** 1 人日 · **依赖** T-101, T-107

**交付物** `scheduler` 容器（Symfony Scheduler）+ 每日任务：
- 删除 `username IS NULL` 且 `created_at < now() - 7 days` 的僵尸注册行（他们只是一条邮箱哈希，无关联数据，可安全物删）
- 清理过期/已消费的 `otp_challenges`
- 清理 30 天前的 `request_ip_hash`

**验收标准** 集成测试断言各清理任务的边界（第 7 天 vs 第 8 天）；`worker` 与 `scheduler` 在 compose 中分别可独立重启。

**规格引用** §5.2、§8.2、§14.2

> ### 落地记录（[ADR-0022](../adr/0022-daily-cleanup-via-symfony-scheduler-single-replica-no-lock.md)）
>
> - **扩展点是一个标签，不是一张清单。** `Shared\Application\Cleanup\CleanupTaskInterface`
>   经 `_instanceof` 打上 `app.cleanup_task`，`CleanupRunner` 用
>   `#[AutowireIterator]` 收集 —— 与 T-003 的 `SeederInterface` / `SeedCommand`
>   逐字同构。**T-204 / T-402 / T-403 / T-404 接入清理 = 加一个实现类**，
>   不改 runner、不改时刻表、不改 compose。
> - **两个入口共用一个 runner**：scheduler 每天 04:30 派发的 `RunDailyCleanup`，
>   以及运维手动的 `bin/console app:cleanup [--task=…]`。所以「手动跑的」
>   与「自动跑的」不可能是两件事。
> - **保留期是配置，不是常量**：`config/packages/ncards_cleanup.yaml`。
>   改任何一个数都要连着 §8.2 的 ROPA 表一起改 —— 代码与 ROPA 不一致是合规问题，
>   不是文档滞后。
> - **`otp_challenges` 的宽限期是 24 小时**（死后才起算）。留一天是为了排障
>   （「昨晚那批登录失败是码错了还是过期了」），而这张表每行都带
>   `email_encrypted`，所以这个数字就是 §8.2 那一行的保留期本身。
> - **`ForgetOtpRequestIpsTask` 在当前配置下恒处理 0 行，这是对的。**
>   挑战 10 分钟过期、24 小时后整行就没了，活不到 30 天。它是 §8.2「ip_hash 30 天」
>   这条**上限**的强制点 —— 上限与「整行什么时候删」是两条独立的承诺。
>   ⚠️ **别把它当死代码删掉**：把宽限期调到 30 天以上是一个完全合理的排障诉求，
>   而调完之后没有任何别的测试会红，只有这道闸还在原地。
> - **僵尸行删除用批量 DQL DELETE**，`devices` / `sessions` 靠库层
>   `ON DELETE CASCADE` 跟着消失（ORM 的 cascade 在批量 DQL 上一行都不生效 ——
>   `DoctrineUserRepositoryTest` 专门钉了这一点）。`cards.owner_id` 的
>   `ON DELETE RESTRICT` 不做跨模块排除（§4.2 规则 5），真撞上就让它炸，
>   由 runner 隔离成「只有这一个任务失败」。
>
> ### ⚠️ 留给后续任务的四条
>
> - **`is_decoy` 删列没做，本卡只切读。** ADR-0014 把删列归给了 T-113，
>   ADR-0022 决定 8 收窄了那句话。**前置条件**：本卡上线 ≥ 2 周（§13.5 的 N+2）
>   且期间没有回滚计划（ADR-0010：生产回滚只回镜像 tag、不回迁移，
>   而旧镜像仍然 `SELECT is_decoy`）。

>   ④ 改 `tests/Double/Identity/IdentityEntities::decoyChallenge()` ——

>   ⚠️ **少做②或③中的任何一个，`composer migration:check` 第 ③ 步

> - **T-405（可观测性）**：§14.4 已加 `cleanup_runs_total` / `cleanup_rows_total` /

## T-114 Vault policy 的下发执行者与漂移检测

**角色** OPS · **预估** 1 人日 · **依赖** T-005, T-012

> ### 缘起：staging 上登录整个不通，而所有绿灯都是绿的（2026-09-19）
>
> 真机验 T-155 的清单时第一步就走不过去 —— OTP 收得到，码填对了，
> `POST /auth/otp/verify` 返回 **503**：
>
> ```
> {"code":"service_unavailable","detail":"The JWT signing key could not be read."}
> ```
>
> | 证据 | 说明 |
> |---|---|
> | `POST /auth/otp/request` → `202` | transit 的 encrypt / hmac 都通，AppRole 本身是好的 |
> | 错码 → `401 token_invalid` | 挑战查库、限流、常量时间预算都正常 |
> | **对**的码 → `503` | 卡在 `SessionIssuer` 事务之后的 `tokens->sign()` |
> | 用 App 自己的 AppRole 读 `secret/data/ncards/jwt/current` → **403**（不是 404） | 密钥在，是**权限不足** |
> | 该 token 的 `token_policies` = `["ncards-app"]` | policy 挂上了，只是内容旧 |
> | staging 唯一一次 `bootstrap.sh` = **2026-09-04**（T-012, `f4adf3c`） | `git log` |
> | `secret/data/ncards/jwt/current` 这行 **2026-09-07** 才进 `ncards-app.hcl`（T-104, `9802110`） | `git log -S` |
>
> 也就是 staging Vault 里的 `ncards-app` **停在 9-04 那一版**。
> `bootstrap.sh` 写 policy 时刻意是**幂等覆盖**，注释里写着「policy 文件是仓库里的
> 真相源，每次跑都应该把 Vault 里的对齐到文件的内容」—— 那条纪律是对的，
> 但在长期运行的环境上**没有任何执行者**。
>
> ⚠️ **为什么没有一个门禁看得见它**（三件事叠起来，各自都合理）：
> - `docker-compose.prod.yml` 把 `vault-init` 设成 `profiles: ["disabled"]`（T-005 的正确决定）；
> - ansible 的 `deploy.yml` / `site.yml` 不碰 Vault（ADR-0004：要 root token 的事永远人工）；
> - CI 每次跑测试都在**自己那个临时 Vault** 上重跑一遍 `bootstrap.sh`
>   （`.github/workflows/backend.yml`），所以 CI 里的 policy 永远是最新的。
>
> 于是漂移只存在于长期运行的环境，而那里恰好没有人在看。
> `/health/ready` 也**结构性地**看不见：`VaultHealthCheck` 打的是免认证的 `sys/health`，
> 它证明的是「Vault 活着、没封印」，不是「这个 AppRole 读得到它要读的东西」——
> 那个类的注释本来就是这么写的。

**交付物**
- 一个**只下发 policy** 的执行者（ansible task 或一条脚本目标），对长期运行的环境幂等可重复跑。
- 漂移检测：把 Vault 里的 policy 与 `infra/vault/policies/*.hcl` 逐字对账，不一致即红。
- 冒烟测试补一条**真的走完 `otp/verify`** 的断言（见下）。
- `docs/runbooks/staging-first-boot.md` 与部署 runbook 各补一步，写明「policy 会随代码演进」。

**实现要点**
- **执行者只许覆盖 policy，绝不许碰 KV。** `bootstrap.sh` 里密钥那段是「已存在就跳过」，
  理由是覆盖签名密钥 = 全部在线 access token 立刻失效（§7.1）。
  把整个 `bootstrap.sh` 塞进部署会同时继承这个风险，还要 root token。
- **不要为此打破 ADR-0004 的分界线**（「凡是需要 unseal key 或 root token 的，永远是人工」）。
  写 policy 只需要 `sys/policies/acl/*` 的 `create`/`update`，那是 `ncards-ops` 的范围 ——
  出路是给 `ncards-ops.hcl` 加这条路径（并在 PR 里回答 `ncards-app.hcl` 抬头那个问题），
  或者保持人工下发但**必须**有漂移检测兜底。二选一，别两个都不做。
- **漂移检测比自动下发更重要。** 自动下发只保证「部署那一刻是对的」，
  而这次的故障是「上一次部署之后仓库里的 policy 又变了」。
- 检测要能跑在**不持有 root token** 的身份上 —— 否则它自己就成了一个需要人工的步骤，
  于是永远不会被定期跑。`sys/policies/acl/<name>` 的 `read` 是最小够用的权限。
- ⚠️ `secret/data/ncards/jwt/previous`（T-105 加的）在 staging 上同样缺。
  今天读不到是**稳态**（轮换前它本来就 404），但轮换那天的症状是「旧 token 全部
  静默失效」—— 正是 `ncards-app.hcl` 里那段注释担心的事。修的时候两条一起对齐。

**验收标准**
1. 在 staging 上把 `ncards-app` 对齐到仓库文件之后，真机走一遍 OTP 能登录成功（`verify` 返回 `200`）。
2. 人为在 Vault 里删掉 policy 的任意一条路径 → 漂移检测红，且报出是哪一条。
3. 冒烟测试在「policy 缺 JWT 那条路径」的环境上**必须红**。
   ⚠️ `scripts/ci/smoke-staging.sh` 今天只打 `/health/live` 与五个安全响应头，
   **一个 `/v1` 端点都不碰** —— 这次故障期间它当然全绿，`/health/ready` 也返回 `200`。
   补一条真的走完「请求码 → 验码」的用例是这一项唯一可信的判据；
   它需要一个 staging 专用的测试邮箱与读信方式，那正是本卡里最费事的一步，
   别把它省成「打一下 `/v1/config` 看是不是 200」。

**规格引用** §17.4、§7.4、§13.8、[ADR-0004](../adr/0004-manual-vault-unseal.md)

> **给生产首启的一条**：生产（`api.n-cards.de`）此刻还没开机，所以还没中招。
> 但它一开机就会踩同一个坑 —— 首启当天写进 Vault 的 policy 是**那一天**仓库里的版本，
> 之后每一次 `ncards-app.hcl` 的改动都会重新拉开同样的缝。

> ### 落地记录
>
> 选的是卡面二选一里的**前一条**（自动下发 + 事后逐字对账）。后一条
> （人工下发 + 只做检测）被否掉的理由是**修复成本**：staging 的 root token
> 首启当天就吊销了，保持人工下发意味着每改一行 policy 都要一次 3 人到场的
> `generate-root`，于是它实际上永远不会被下发 —— 那正是本卡的故障本身。
>
> ⚠️ **但没有照卡面那样往 `ncards-ops.hcl` 上加，而是新开了一份
> `ncards-policy.hcl` + 同名 AppRole。** 卡面原话是「给 ncards-ops.hcl 加这条
> 路径」，先那样落地过，然后拆了出来 —— 理由见下面「为什么不复用 ncards-ops」。
>
> 形状：
>
> ```
> infra/vault/_vault_api.sh     api / status_of / body_of / wait_for_vault（与 bootstrap.sh 共用）
> infra/vault/policy-sync.sh    check | push，只碰 policy，走 AppRole ncards-policy
>        ▲
>        │ compose 服务 vault-policy（profiles: ["ops"]，与 vault-init 同镜像换 entrypoint）
>        │
> roles/ncards_stack/tasks/vault_policy.yml   排在 env 之后、snapshot 之前，tag: vault-policy
>        │
>        └─► 判定只出 fact，**处置在 deploy.yml**（漂移不回滚，与 VAULT_SEALED 同形）
> ```
>
> 现在是**三份 policy、两个 AppRole**：
>
> | policy | AppRole | 谁在用 | 节奏 |
> |---|---|---|---|
> | `ncards-app` | `ncards-app` | 后端 app / worker | 每个请求 |
> | `ncards-ops` | 还没有（T-404 会建） | 轮换与 rewrap | 一年几次，人工 |
> | `ncards-policy` | `ncards-policy` | 部署流水线 | **每次部署，自动** |
>
> ### ⚠️ 三个坑，三个都是实测撞出来的
>
> | 位置 | 写错的样子 | 症状 |
> |---|---|---|
> | `check_policy` 里读 Vault 那份 policy | `jq -r` | **每一份 policy 都被判成漂移**。Vault 存的就是文件的原始字节、末尾换行也在里面，`-r` 会再补一个 —— 一个恒红的检测器与没有检测器是同一回事。必须 `jq -j` |
> | `push` 遇到 403 | `return 1` | **每次部署都红**。`ncards-policy` 给自己那条路径刻意只有 `read`（有 `update` 就能自提权到 `sudo`），于是下发时它必然写不了自己。正解是降级成「这一份只对账」 |
> | `push` 的写入时机 | 无条件覆盖 | ansible 永远报 changed，且每次都去撞上面那个 403。改成**先探测再写**之后，稳态下一次都不写、一次都不撞 |
>
> ### ⚠️ 为什么不复用 `ncards-ops`（这是本卡对卡面的唯一一处偏离）
>
> `ncards-ops` 持有 `transit/keys/+/rotate`，而那个通配符**覆盖到 `ncards-hmac`** ——
> 轮换它会让全部 `email_hash` 查找失效，且 HMAC 单向、**不可补救**
> （见 `CryptoKey::isRotatable()`）。把两条 `sys/policies/acl/…` 挂在它身上，
> 等于让**每次部署都要用到的**那份凭据连带握着一条能毁掉全部账号查找的命令，
> 而本卡需要的只有「读写 policy」。
>
> 两个身份的使用节奏也完全不同，这才是分家的根据：
>
> | | 用途 | 频率 | 凭据在哪 |
> |---|---|---|---|
> | `ncards-ops` | T-404 的轮换与 rewrap | 一年几次 | 还没签发 |
> | `ncards-policy` | 每次部署下发 policy | 每次合入 | sops + 部署主机的进程环境 |
>
> 拆开之后，**部署流水线失陷的爆炸半径里没有任何 transit 能力**。
>
> ### 三件事**没有**做，都是刻意的
>
> - **不给 `sys/policies/acl/*` 通配**，逐条给 `ncards-app` / `ncards-ops`（读写）
>   与 `ncards-policy` 自己（只读）。将来新增 policy 要显式加行 ——
>   漏加的症状是部署时那一份报 403 并降级成只对账，看得见，不是静默。
> - **`ncards-policy` 不给自己 `update`。** 有它就能把自己改写成
>   `path "*" { capabilities = [..., "sudo"] }`，那等于这份清单不存在。
>   代价是改 `ncards-policy.hcl` 本身要一次 generate-root 仪式，接受。
> - **执行者一行 KV 都不碰。** 把整个 `bootstrap.sh` 塞进部署会连同「探测返回 5xx
>   被误读成不存在 → 覆盖 JWT 签名密钥 → 全部在线会话失效」那条路径一起继承。
>
> ### 分家由一个用例守着，不靠注释
>
> `backend/tests/Integration/Shared/Vault/PolicyAppRoleTest`（与既有的
> `AppRolePolicyTest` 同形）：正面验它读得到三份、写得了该写的两份；
> **反面逐条验它一条 transit 都没有**，且改不了自己那份 policy、没有通配、没有 list。
>
> 实测过它真的守得住：把 bootstrap.sh 的 `token_policies` 改回带 `ncards-ops`，
> 4 条断言当场红，第一条点名的就是 `transit/keys/ncards-hmac/rotate`。
> 没有它的话，「往 ncards-policy.hcl 里粘一条 transit」或「图省事改回 ncards-ops」
> 都不会让任何东西变红。
>
> ### 冒烟：`scripts/ci/smoke-otp.py`
>
> `scripts/ci/` 下第一个非 bash 脚本（理由见文件头：bash 里做 IMAP over TLS 只能靠
> `openssl s_client` 手搓）。判据只有一个 —— **`verify` 真的返回 200**。
> ⚠️ 别用 `otp/request` 的 202 冲抵：那一步只用 transit 的 hmac/encrypt，**不读**
> JWT 签名密钥，故障期间它照样 202。
>
> 两个副作用写在卡面上：每次 main 合入发一封信（staging 与生产**共用**发信配额），
> 且首次 `verify` 成功会在 staging 建一行 users。生产入口（`deploy-manual.yml`）
> 因此默认留空不跑。`device.id` 是**固定**的 UUID —— 每次换新 id 等于每次部署都往
> `no-reply@` 那个没人看的收件箱多塞一封「新设备登录」提醒。
>
> ### 合入之后还有一步人工
>
> staging 已经首启过、root token 已吊销，而写 `ncards-policy` 这份新 policy
> 与建同名 AppRole 都要 root（这台机器上还没有任何身份能写 policy —— 那本来
> 就是本卡要修的洞）。
> 所以要做一次 `generate-root` 仪式（3 位 unseal key 持有人到场），步骤写在
> `docs/runbooks/staging-first-boot.md` 的「已经首启过的环境怎么补上」。
> **这是最后一次需要 root 的 policy 变更。** 在它做完之前，部署里那一步会打
> 「跳过」并放行 —— ⚠️ **跳过不是通过**，那期间仓库与 Vault 之间仍然没有门禁。

## T-150 令牌存储与网络认证层

**预估** 1.5 人日 · **依赖** T-009, T-010

**交付物** `data:auth` Repository + OkHttp `Authenticator`/`Interceptor`：附加 Bearer、401 `token_expired` → **静默刷新后重试一次**、401 `token_invalid` → 清空本地会话跳登录。

**实现要点**
- Access token 存内存 + `EncryptedSharedPreferences`；refresh token **仅存** `EncryptedSharedPreferences`。
- 刷新必须串行化（Mutex），避免并发 401 触发多次轮换——**轮换重放检测会把用户踢下线**。
- 错误映射对 `code` 分支，**不得解析 `detail`**。

**验收标准** 单测：并发 5 个 401 只触发一次刷新；`token_invalid` 会清空本地会话。

**规格引用** §6.1、§7.1、§7.3

> ### 落地记录
>
> **范围比卡面宽一档**：`data:auth` 一次成型，除令牌存储与认证层外还包含
> `requestOtp` / `verifyOtp` / `consumeMagicLink` / `fetchMe` / `logout`。
> 理由是 §12.3 不允许 feature 层直接调 `AuthApi`，那几个调用早晚要落在
> `data:auth`；分两卡写只会让 T-151 一边做 UI 一边补 Repository。
> **T-151 因此只写 UI 与 ViewModel，不再往 `data:auth` 加生产代码。**
>
> ### ⚠️⚠️ 两个坑，两个都在验收标准的正路上
>
> - **`maxRequestsPerHost = 5` 会让「并发 5 个 401」死锁。** OkHttp 的
>   `Dispatcher` 默认 `maxRequests = 64` 但 **`maxRequestsPerHost = 5`**，而
>   `Authenticator` 是在这条 call 仍占着 `runningAsyncCalls` 槽位时被调用的。
>   于是 5 条 call 全停在 `authenticate()` 里占满槽位，刷新请求是第 6 条，
>   进 `readyAsyncCalls` 永远不被提升 —— **集体卡到读超时**，不是一个看得出
>   原因的错误。解法是刷新走一个拥有**独立 `Dispatcher`** 的客户端。
>   ⚠️ `OkHttpClient.newBuilder()` 默认**共享** dispatcher 与连接池：
>   连接池共享是想要的，dispatcher 必须显式 `.dispatcher(Dispatcher())` 换掉。
>   把 `maxRequestsPerHost` 调大不是解法 —— 那只是把并发阈值往上挪。
> - **Mutex 只保证串行，不保证「只刷新一次」。** 光有锁的话 5 个并发 401 会变成
>   5 次**排队的**刷新，而第 2 次就命中 `previous_token_hash` = 令牌被窃判定。
>   真正让验收标准成立的是 `RefreshGate` 拿到锁之后的**快速通道**：
>   比较「我这次失败时用的那一枚 access token」与存储里当前那一枚，
>   不同就说明前一个持锁者刚换过，直接用新的重发。
>   （比「存储里有没有值」是错的 —— 那永远为真。）
>
> ### 结构：两个反转的插槽 + 两条客户端
>
> `:core:` 不得依赖 `:data:`（`ModuleGraph` 配置期强制），所以
> `core:network:impl` 只声明插槽（`di/AuthSlots.kt`：`@BindsOptionalOf Authenticator`
> + `@Multibinds @AuthInterceptors Set<Interceptor>`），实现由 `data:auth` 绑进来。
> 形状与后端 ADR-0018 的 `OnboardingStatusInterface` 是同一条依赖倒置。
>
> ```
> @Unauthenticated OkHttpClient ─► @Unauthenticated Retrofit ─► @Unauthenticated AuthApi
>         │                                                            │（刷新只走这条）
>         │ newBuilder().dispatcher(Dispatcher())                      ▼
>         ▼                                                      RefreshGate（Mutex）
>     OkHttpClient（+ SessionAuthenticator + BearerAuthInterceptor）
> ```
>
> 这个形状顺带**消掉了 Dagger 环**（`OkHttpClient ← Authenticator ← AuthApi ←
> Retrofit ← OkHttpClient`），不需要 `Lazy` / `Provider`。
>
> ### 三条别顺手改的
>
> | 位置 | 别改成 | 为什么 |
> |---|---|---|
> | `SessionStore.clear()` 里的两次 `secrets.remove(...)` | `secrets.clear()` | `KeystoreSecretStore.clear()` 连**包裹密钥一起丢弃**，而 SQLCipher 的 `db_passphrase` 就在同一个门面下 —— 登出会把用户整个本地库连同 `sync_outbox` 里没推上去的写入变成永远解不开的密文。**功能测试完全看不出来**（重新登录时库已被当成「首次安装」重建） |
> | `PublicEndpoints` 里那张逐条列出的路径表 | `startsWith("auth/")` | 免鉴权的五个端点里三个在 `auth/` 下，但 `auth/logout` **需要** Bearer。用前缀的后果是 logout 永远发不出去而没有任何迹象（服务端 401，本地照样清会话，用户看到「登出成功」）。与后端 `AuthenticationListener` 的类注释是同一个坑的两侧 |
> | `RefreshGate.idempotencyKeyFor()` 的导出式 UUID | `UUID.randomUUID()` | 随机 key 只能盖住 `RetryInterceptor` 在同一次调用内的重试。「整个调用失败了、下一个 401 又来一次」这条路径上，随机 key 会让旧令牌配新 key 打过去 —— 正中重放检测，用户收到一封「令牌可能被窃」并被登出 |
>
> ### 刷新失败的处置表里**只有一行清会话**
>
> `token_invalid` 清；429 / 503 / 409 / 426 / 网络 / 500 一律**保留会话**。
> 把 503 压成登出，后果是一次维护窗口把全体用户踢回登录页，而登录本身在那个
> 窗口里也是坏的 —— 与后端 `AuthenticationListener` 拒绝把 Vault 故障压成 401
> 是同一条理由。
>
> ### 证据
>
> 34 个新单测（`:data:auth` 31 / `:core:network:impl` 新增 3）：
> 覆盖率 `:data:auth` 87.9%、`:core:network:impl` 88.4%（门禁 70%）。
> `ktlintCheck` / `detekt` / `:app:lintDebug` / `:app:assembleDebug` 全绿。
>
> 验收标准的两条各有专门的用例：
> `SessionAuthenticatorConcurrencyTest`（真 `MockWebServer` + 真并发 5 条 call，
> 断言打到刷新端点**恰好 1 次**；删掉快速通道当场变红，已实测）与
> `SessionAuthenticatorTest.clearsSessionOnTokenInvalid`（顺带断言
> `server.requestCount == 0` —— `token_invalid` 连刷新都不该试）。
>
> `NetworkAuthSlotsTest.doesNotShareDispatcher` 守的是上面那个死锁：
> 它断言两条客户端不共享 `Dispatcher` 但共享连接池。
>
> ⚠️ **DI 图今天没有编译期保护。** `:app` 里还没有人注入 `AuthRepository` 或
> `OkHttpClient`（第一个真实消费者是 T-151 的 NavHost），而 Dagger 默认只校验
> **可达**的绑定 —— 插槽是可选的，绑错了图照样建得起来，只是每个请求都不带
> Bearer。本卡是这样验的：临时往 `:app` 加一个 `@EntryPoint` 暴露这两个类型，
> 跑 `:app:assembleDebug`，确认生成的 `DaggerNcardsApplication_HiltComponents_SingletonC`
> 里 `provideOkHttpClient(…, Optional.of(authenticator), …)` 成立且无环，然后删掉。
>
> ### 留给后续任务的五条
>
> - **T-151**：`:app` 启动时必须调一次 `AuthRepository.restoreSession()`（在协程里）——
>   令牌是懒加载的，不调它 `sessionState` 会一直停在 `Unknown`，NavHost 一直显示
>   splash。三态直接驱动起始目的地；`Unknown` 期间显示 splash，**不要**跳任何地方。
> - **T-151**：`403 username_required` **不**由 `Authenticator` 处理 —— 它不是 401，

>   `fetchMe()`，**不要**试图从 access token 里读（ADR-0018 拒绝了 `onb` claim，

> - **T-158**：`MetaApi` 还没有 provider，加在 `NetworkModule` 里（`MeApi` 本卡已加）。
>   升级墙的信号是 `GET /v1/config` 的 426，不是本地比较版本号。
> - **证书固定（§7.2 T15）**：本卡不做，已在 §7.2 记为「已接受风险」并写明

> - **`:core:testing` 仍然是空壳**：本卡的 `FakeSecretStore` 是第二份拷贝

> 客户端误拒一个合法名字才是不可自助的故障（username 不可变，T-108 的拦截器
> 还挡着注销路径）。`UsernameRulesTest` 有一条用例专门断言那 12 个词在本地被放行，
> 就是为了让「以后有人顺手抄进来」当场变红。

> **`POST /me/username` 带一个由归一化后的名字导出的 `Idempotency-Key`。**
> 这不是为了重试（`RetryInterceptor` 对不带 key 的 POST 一律不重试），
> 是为了「服务端已经记上了、响应在路上丢了、用户再按一次确认」这条路径 ——
> 不带 key 就白烧掉 10 次里的一次，而用尽 = 账号永远进不了钱包。
> 形态与 `RefreshGate.idempotencyKeyFor()` 同构（导出式而不是 `randomUUID()`）。

> ### ⚠️ 语言切换牵出一条三件套的连锁
>
> J1 第一屏要**真的**切界面语言，唯一代价最小的路是
> `AppCompatDelegate.setApplicationLocales`。它拉出三件必须同时做的事，

## T-152 `core:barcode` 渲染与格式映射

**预估** 1.5 人日 · **依赖** T-008

**交付物** ZXing `MultiFormatWriter` → `BitMatrix` → Bitmap 渲染器 + **唯一**的 `BarcodeFormat` 枚举（ML Kit ↔ ZXing ↔ 展示名的映射集中在 `core:model`）。

**实现要点**
- **必须按目标 `View` 尺寸生成**（不要生成小图再放大——边缘模糊会导致扫码枪读不出）。
- **必须强制白底黑码**，无论 App 主题深浅。深色模式下的条码是扫码失败的经典原因。
- 1D 码 `margin` 至少 10 模块宽（静区），否则部分扫码枪拒读。
- 渲染在 `Dispatchers.Default`，结果缓存于内存 LruCache（key = format + value + size）。
- **禁止**在各处散落 `when` 做格式映射。
- 支持码制：EAN-13/8、UPC-A/E、Code 128/39/93、ITF、Codabar、QR、Aztec、PDF417、DataMatrix。

**验收标准** 单测覆盖全部码制的映射往返；真机上用扫码枪/另一台手机实测能读出 EAN-13 与 QR。

**规格引用** §1.3、§10.1

> ### 落地记录（2026-09-12）
>
> ```
> core:model    barcode/BarcodeFormat.kt    13 个码制 + UNKNOWN，wireName / dimension / fromWire()
> core:barcode  format/BarcodeFormatTable   ← 全仓唯一的 when(format)，一次产出三列
>               render/QuietZone            静区表（模块/每侧）
>               render/BarcodeRasterizer    纯 Kotlin：1× 矩阵 → 静区 → 整数缩放 → ARGB
>               render/BarcodeRenderer      唯一入口（suspend → Bitmap）
>               cache/SizedLruCache         泛型、按字节、sizeOf 注入
> ```
>
> ### §10.1 的字面要求做不到，拆成了两处
>
> §10.1 写「三列映射必须集中在 `core:model` 的单一枚举中」，而 `core:model` 是
> `ncards.jvm.library`：看不见 ML Kit 的 `Barcode.FORMAT_*`（Android 常量），
> 也没有 `res/` 放展示名。§12.3 又把 `core:barcode` 称作「格式映射唯一实现处」。
>
> 取两者的实质交集：**词汇表在 `core:model`，三列适配在 `core:barcode`，
> 但全仓只有一个 `when (format)`**，它一次产出三列。加第 14 个码制会在那一处
> 编译失败，三列被迫同时补齐 —— 比字面照做更严格（三个各自穷举的 `when`
> 反而允许漏改其中一个）。理由与被否决的方案见 [ADR-0023](../adr/0023-barcode-format-vocabulary-in-core-model-adapters-in-core-barcode.md)。
>
> ### ZXing 的静区语义有**五套**，其中两套压根不存在
>
> 这是本卡最要紧的发现，逐条实测（zxing 3.5.4）：
>
> | 码制 | 读 `MARGIN`？ | 默认 | 单位 |
> |---|---|---|---|
> | Code 128/39/93、ITF、Codabar | 是 | 10 | 模块，**两侧总和**（每侧 5） |
> | EAN-13/8、UPC-A/E | 是 | **9** | 模块，**两侧总和**（每侧 4.5） |
> | QR_CODE | 是 | 4 | 模块，**每侧** |
> | PDF_417 | 是 | 30 | **输出像素**，每侧 |
> | **AZTEC、DATA_MATRIX** | **否，完全忽略** | **0** | 没有静区 |
>
> 照 §10.1 字面传 `MARGIN = 10`，得到的是一维码每侧 5 模块，而 Aztec 与
> DataMatrix **一圈静区都没有**。实测静区为 0 时 ZXing 自己的 reader 在
> 4 / 12 / 33 px 三档模块宽下全部 `NotFoundException`。
>
> 加上「装不下时 ZXing 静默返回**更大**的矩阵」（五个 writer 都是
> `Math.max(width, fullWidth)`），结论是**静区与缩放必须自己接管**：
> 只向 ZXing 要 `encode(…, 0, 0, MARGIN = 0)` 的 1× 裸矩阵。
> 实测该探针对 13 种码制都返回恰好等于模块数的矩阵
> （EAN-13 → 95×1，QR → 25×25，Aztec → 19×19，DataMatrix → 32×8，PDF417 → 120×24）。
>
> ### 三个「没有症状」的坑，各有测试钉住
>
> - **矩形 DataMatrix 尺寸越大越读不出。** ZXing 默认允许矩形符号（本卡的载荷得到
>   32×8）；实测模块宽 4 px / 12 px 能解，**33 px 解不出** —— 而全屏条码页正是
>   最大的那一档，这个缺陷会精确地只在真机全屏页上发作。改用 `FORCE_SQUARE`
>   （16×16）后三档全通。强制方形不改变码值。
> - **缓存地板曾定成 2 MiB，装不下一张全屏图。** `SizedLruCache.put` 会因为
>   「单个值比预算还大」直接不收，缓存变成死重而**功能全对**，只是每次都重算。
>   地板改成 5 MiB（1080×1080 ARGB ≈ 4.45 MiB），`BarcodeCacheBudgetTest` 钉住这条不变式。
> - **ZXing 的异常消息里嵌着码值片段**（`Cannot encode : '…'`、
>   `non-encodable character: 'X'`）。`scripts/ci/check-sensitive-logs.sh` 是两段式的，
>   只拦 `barcodeValue` / `rawValue` 出现在日志行的情形，**拦不住 `Timber.w(e)`** ——
>   这是一条现有门禁结构上看不见的 §7.3 / §14.4 泄漏。约定：只记异常类名与码制，
>   永远不记 `e.message`，也不解析它。
>
> ### 三条写测试时被 ZXing 纠正的认知
>
> 都是「我以为这是非法输入，其实 ZXing 收下了」：
>
> - **Codabar 两头都没有起止符是合法的** —— `CodaBarWriter` 会自动补上默认的 `A…A`。
>   真正非法的是**起止符不配对**（有头无尾）。T-155 若要求「必须带起止符」，
>   那是我们自己的规则，不是 ZXing 的。
> - **Code 39 的小写字母是合法的** —— 撞到字符集外的字符时它会自动切到
>   「扩展全 ASCII 模式」。真正编不出来的是**非 ASCII**（德语变音符号就是）。
> - **ZXing 的 reader 默认吃掉 Codabar 的起止符**，要 `RETURN_CODABAR_START_END`
>   才拿得回来；**UPC-A 不给 `POSSIBLE_FORMATS` 会被报成前缀补 0 的 EAN-13**。
>   往返测试里这两条都显式处理了。
>

## T-153 钱包列表

**预估** 2 人日 · **依赖** T-009, T-152（Q7 调色板）

**交付物** `feature:wallet`：Room `Flow` 驱动的卡片列表、搜索、置顶、拖拽排序、颜色/首字母图标、空状态、`sync_state` 徽章。

> **② 搜索没进 SQL。** 直觉上该是 `CardDao` 里一句 `LIKE`，三条理由否掉它：
>
> - **SQLite 的 `LIKE` 对德语是错的。** 它的大小写折叠只覆盖 ASCII，
>   `Ä` 匹配不到 `ä`，而本库 schema 里**一个 `COLLATE NOCASE` 都没有**。
>   给一个德国市场的 App 写一个匹配不了变音符号的搜索，是把 bug 写进地基。
> - **数据量够不着。** §7.5 每用户上限 500 张卡，规格自己注明「P99 < 30」。
> - **加 `LIKE` 要把 `observeWallet` 那段 SQL 复制第二份**（两个 JOIN + 一个派生
>   `sync_state` 的子查询）。两份迟早漂移 —— 这正是 T-009 拒绝给 `cards` 加
>   `sync_state` 列时用的同一条理由。
>
> 于是 `CardRepository.observeWallet()` **不收查询词**，ViewModel 用 `combine`
> 在一条只订阅一次的流之上过滤。传进去的话每敲一个字母都要重订阅一次 Room，
> 中间还会闪一帧空列表。匹配规则是 `core:model` 的 `Card.matches(query)`
> （纯函数，在有覆盖率门禁的模块里）。
>
> ⚠️ 顺带钉死一个 locale 陷阱：折叠用 `Locale.GERMAN` 而不是默认 locale ——
> 土耳其语的 `I` 小写是无点的 `ı`，用默认 locale 的话 `"ITF"` 在土耳其语设备上
> 搜不到。那种 bug 只在那一种设备上现形，本机永远测不出来。
>
> ⚠️ 别把 §3.8 C4 的「搜索不作输入提示、无 typeahead」套到这里 ——
> 那条讲的是**好友 username 搜索**（一个账号枚举面）。本地卡片过滤不发请求。
>
> **③ 拖拽排序手写，没引库。** `libs.versions.toml` 的规则第 3 条是
> 「只声明已经在用的东西」，而成熟的重排库解决的是一个宽得多的问题
> （多列、嵌套、自动滚动）。本屏要的是单列单区段重排，那是 `ReorderableListState`
> 那一百来行。
>
> ⚠️ **拖拽状态不进 ViewModel。** 手指每移动一像素都会更新位移，放进
> `StateFlow<UiState>` 就是每帧一次全列表重组 —— 200 张卡会肉眼可见地掉帧。
> 位移住在 Compose 的局部状态里，只有松手那一刻才写一次 Room。
>
> 落点算法用 `LazyListState` 里**每一项真实的 offset 与 size**，不是「位移 ÷ 行高」：
> 行高不是常量（标题两行、德语长词换行、字体 200% 时整行长高）。
>
> `sort_order` 用**受影响区间的稠密重排**，不用稀疏间隔 —— 服务端
> `PUT /cards/{id}/placement` 对它**没有任何归一化契约**，稀疏值在多设备合流后
> 照样会撞，等于白付复杂度。只写真的变了的那几行（一次拖拽通常只动一小段，
> 而每行都要配一条 outbox）。
>
> ⚠️ 置顶**不动** `sort_order`：查询是 `ORDER BY is_pinned DESC, sort_order ASC`，
> 两个维度正交。实现成「改 sort_order 到最小」会让取消置顶后原位置永久丢失。
>
> ⚠️ outbox 写的是 `entity_type = 'card_member'` 而不是 `'card'`。这不只是分类
> 准确：`observeWallet` 派生 `sync_state` 时**只看 `'card'`**，写错的话用户每置顶
> 一次就会看到一个「待同步」角标，而那是假的（placement 不参与 revision）。
>
> **④ `WalletUiState` 的 `Empty` 与「搜索无结果」是两格，不是一格。**
> §10.4 的四格照落（本卡就是那四格设计给的列表页，而 `feature:onboarding`
> 刻意偏离过，它的注释解释了为什么向导不适用）。但多了一条约束：
> 搜索无结果**仍然是 `Content`**（`cards` 空、`query` 非空、`totalCount` > 0）。
> 并成一格的后果是一个有 40 张卡的用户搜错一个字母，看到「你还没有任何卡，
> 添加第一张吧」—— 既是谎话，给的出路也是错的。单测与仪器测试各有一条守着它。

> ### 无障碍：拖拽必须有一个非手势的等价物
>
> TalkBack 打开时长按会被无障碍服务**拦截**，所以只做拖拽等于把「排序」这个
> 交付物对视障用户整个关掉 —— 而 §11.2 的目标用户里明确包含银发与视障群体。
> `WalletCardRow` 因此挂了 `customActions`（置顶 / 向上移动 / 向下移动）。
> §11.2 把「无障碍服务的自定义动作」列在**可后置**里，但对这一屏它不可后置：
> 没有它就没有等价路径。

## T-154 卡详情与全屏条码页

**预估** 2 人日 · **依赖** T-152, T-153

**交付物** 卡详情页 + **独立 `Activity`** 的全屏条码页。

**实现要点**
- 亮度 = `1.0f`；`FLAG_KEEP_SCREEN_ON`；**`onPause` 必须恢复原亮度**（否则用户会投诉耗电）。
- 支持横屏放大 1D 码。
- **无障碍硬要求（不是可选项）**：码值必须以**可选中的大字号文本**显示在条码下方，带 `contentDescription`，使 TalkBack 用户能让系统朗读、口述给收银员。这是银发用户与视障用户的关键功能。
- 性能预算：Widget 点击 → 条码完全渲染 P95 ≤ 800 ms（冷启动 ≤ 1.8 s）。
- SHOULD：设置项"允许截屏"（默认允许；关闭时加 `FLAG_SECURE`）。

**验收标准** Macrobenchmark 达标；TalkBack 能读出码值；退出后亮度恢复。

**规格引用** §9.1、§10.2、§11.2

> ### 落地记录（2026-09-13）
>
> 钱包 → 详情 → 全屏条码三步都通了。T-153 押的注兑现：`NcardsNavHost.kt` 的
> `onOpenCard` 只改了一行。
>
> 本卡同时是**条码渲染器的第一个真实消费者** —— 在它之前 dex 里搜不到一个字节的
> ZXing，因为没有人调用渲染器，R8 把整条链删了。
>
> ### 相对任务卡的四处偏差，每条都有理由
>
> **① 全屏页的 `Activity` 在 `:app`，界面在 `feature:carddetail`。**
> 任务卡把这一页整个划给了本卡，最省事的读法是「Activity 也放 feature 里」。
> 那条路会踩进一个**没有任何报错**的坑：per-app locales
> （`AppCompatDelegate.setApplicationLocales`）在 **API < 33 上只对 AppCompat
> 组件生效**，而 minSdk 是 26 —— 一个住在 feature 里的纯 `ComponentActivity`
> 会让这一页用**系统语言**而 App 其余部分用用户选的语言。编译、lint、单测、
> Compose UI 测试全都看不出来。
>
> 而把它做成 `AppCompatActivity` 要求 androidx.appcompat，`libs.versions.toml`
> 对那条依赖的注释是明令：「**只给 :app**……**不要**因为『反正引进来了』就在
> feature 里用 appcompat 的任何东西」。
>
> 第三条理由让这个划分本来就自然：这个类拥有的**全部**东西 —— 亮度、
> `FLAG_KEEP_SCREEN_ON`、`FLAG_SECURE`、manifest、`exported="false"`、边到边、
> `reportFullyDrawn` —— 都是**窗口**的事，而窗口与 manifest 本来就住在组装层。
> §12.3 的分层一点没破：界面仍然在 feature 里。
>
> **没有写 ADR**：按 CONTRIBUTING §6 的四条门槛都够不着（没有新的跨模块依赖 ——
> `:app → :feature:carddetail` 早就存在，`:feature: → :core:` 是规则允许的；
> 没有改数据模型语义；没有推翻 §2）。理由写进了三处代码注释与
> `android/README.md` 的新小节。ADR-0023 的做法可以对照：那一卡写 ADR 是因为
> §10.1 的字面要求**不可能执行**，这里不是。
>
> **② 单卡读取没有加第三份 SQL。** 详情页要 `role`（gate 编辑入口）、`isPinned`、
> 派生的 `sync_state`，也就是 `CardDao` 里那段带两个 JOIN 和一个派生子查询的
> 查询 —— 而那段 SQL 在 `CardDao` 里**已经逐字存在两份**（`observeWallet` 与
> `walletSnapshot`），它自己的 KDoc 写着「改上面那段的人必须同时改这一段」。
>
> 所以 `CardRepository.observeCard(id)` 建在 `observeWallet()` 之上：
>
> ```kotlin
> observeWallet().map { it.firstOrNull { c -> c.id == cardId } }.distinctUntilChanged()
> ```
>
> `core:database` 一行没改。与 T-153 把搜索留在内存里是同一条理由
> （§7.5 每用户上限 500 张，规格自注「P99 < 30」）。
>
> ⚠️ `distinctUntilChanged()` 在这里**不是**空操作（与 `observeWallet` 上那句
> 「`StateFlow` 自带去重」说的不是一回事）：上游是钱包全表，别的卡动一下它就发
> 一次，而本流的值没变。有一条专门的测试用 `expectNoEvents()` 守着它 ——
> 去掉那个操作符，用户在列表里拖动另一张卡时正开着的详情页会跟着重组。
>
> ⚠️ 顺带修正了一处归属：`CardTestDoubles` 里 `CardDao.observeCard` / `findCard`
> 那两条 `NotImplementedError("T-154")` 改成了 `"T-155"`。它们返回**裸**
> `CardEntity`（没有 `role` / `sync_state`），本卡够不着；真正需要它们的是
> 编辑表单（按 id 取一张卡 + `revision` 做 `If-Match`）。
>
> **③ 详情页不画条码，只给一个「Barcode anzeigen」按钮。** 两条理由：一张小条码
> 正是 §10.1 明令禁止的那种东西（小到详情页那个尺寸的一维码，扫码枪本来就读
> 不出，用户会先试一次、失败、再去找那个按钮）；而且画它要多跑一次渲染
> （另一个尺寸 = 另一个缓存 key），而这一页的用户下一步几乎必然是去全屏页。
> 码值以文本形式就在按钮下面，信息一点没少 —— 而那份文本本来就是 §10.2 的
> 无障碍硬要求。
>
> **④ 「删除」与「共享」整个没有画。** M3 的 T-304 明确拥有「owner 删卡确认
> 对话框**必须**显示『该卡正共享给 N 位好友，他们也将失去它』」，而 `data:card`
> 今天连删除路径都没有（outbox 从未写过 `entity_type = 'card'`）。
> 「编辑」按钮画了但**禁用**（T-155 接上），照钱包空状态那个按钮的先例 ——
> 「画出来但按不动，比一个空白屏诚实」。
>
> ### 无障碍：真正会被写错的是 `contentDescription`
>
> §10.2 的原文是「码值必须以**可选中的大字号文本**显示在条码下方，且带
> `contentDescription`，使 TalkBack 用户可以让系统朗读、**口述给收银员**」。
>
> 最容易写出来的版本是 `contentDescription = card.barcodeValue` —— 它在代码
> 审查里看不出任何问题，而 TTS 会把 `4012345678901` 念成「四万零一百二十三亿
> 四千五百六十七万八千九百零一」。收银员听不懂，用户也没法照着念，
> 这个功能等于没做。
>
> 落法是一个纯函数 `spokenBarcodeValue()`：**只对短的、全是数字的**载荷逐字符
> 拆开（`"4, 0, 1, 2, …"`，用逗号不用空格 —— 多数 TTS 对空格分隔的数字串仍会
> 尝试合并成一个数，逗号则强制逐个念并留出停顿，而停顿正是收银员跟着录入
> 需要的）。上限 20 个字符：二维码的载荷动辄上百字符，拆成一个字符一个逗号
> 得到的是一段没人听得完的噪音，比不拆更糟。7 条纯 JVM 单测钉住它。
>
> **可见文本是原样的码值，一个字符都不加。** 把 EAN-13 按 1-6-6 分组确实更好认，
> 但 `SelectionContainer` 里选中复制出来的就会是一串带空格的东西 —— 而用户复制
> 码值多半正是为了粘到别处用。可读性交给等宽字体 + `letterSpacing` + 字号，
> 那三样都不改变字符串本身。
>
> **没有做「复制到剪贴板」的自定义动作**，虽然 T-153 给拖拽做过非手势等价物。
> 剪贴板在旧 API 上可被其他应用读取，而码值在 §14.4 的脱敏清单上。
> 硬要求（TalkBack 能让系统朗读）由那个带描述的可聚焦节点满足，
> 「可选中」由 `SelectionContainer` 满足给视力正常的用户。
>
> ### 四个被实测证实的坑
>
> | 坑 | 症状 |
> |---|---|
> | `Image(..., ContentScale.Fit)` | `Success.bitmap` **可能小于请求尺寸**，`Fit` 会把它**放大** —— 非整数缩放毁掉整数模块宽，正是扫码枪读不出的那种糊。改成 `drawImage(dstSize = 位图自身尺寸)` + `FilterQuality.None` |
> | 一维码高度不封顶 | 横屏满屏是 2400×800 ARGB_8888 = 7.3 MiB，越过条码缓存 5 MiB 的地板 → `SizedLruCache.put` **直接不收**，缓存变成死重且**没有任何症状**。封成 ≤ 0.4×宽且 ≤ 600 px |
> | `MaterialTheme.colorScheme.surface` 当白底 | 浅色配色里它是 `#FDFCFF`，不是纯白；静区不纯白就不是静区。而且 `NcardsTheme` 默认开着 `dynamicColor`（跟壁纸走）。全屏页写死 `Color.White` / `Color.Black`，**并且** `NcardsTheme(darkTheme = false, dynamicColor = false)` —— 两件事缺一不可 |
> | `window.attributes.screenBrightness = 1f` | `window.attributes` 返回的是**副本**，不整体写回去 `WindowManager` 收不到通知 —— 亮度纹丝不动，而代码看起来完全正确。这是这个功能最容易悄悄坏掉的一处 |
>
> 亮度的另外两条：拉满在 `onResume`（写在 `onCreate` 的话，被来电悬浮窗打断再
> 回来屏幕是暗的，而用户正站在收银台前）；恢复在 `onPause` 且恢复成
> `BRIGHTNESS_OVERRIDE_NONE`（窗口级 override 的正确反面是「没有 override」，
> 不是「写死成刚才那个数」）。
>
> ### 「允许截屏」只落了默认值那一半
>
> §7.3 的 SHOULD 是「默认允许；关闭时加 `FLAG_SECURE`」。`core:datastore` 与
> `feature:settings` 今天都是空壳，`libs.versions.toml` 里连 DataStore 都没有 ——
> 为一个布尔值立一个模块不成比例。
>
> 落法是在 `core:common` 开一个 `ScreenshotPolicy` 端口（形状与
> `CurrentUserIdStore` / `AppLanguageStore` 同构），实现在 `:app` 里恒为 `true`。
> **今天的行为与「根本没做这个功能」完全一致**，所以延后不让用户少任何东西；
> 换来的是 `FLAG_SECURE` 的接线此刻就是对的（它有一条不直观的约束：必须在窗口
> 内容确定之前设好，运行中翻转要重建窗口），设置页那一卡只换一个实现类。
>
> ⚠️ 顺带记一笔：§7.3 的另一条 SHOULD「应用切到后台时对最近任务快照打码」
> 靠的是同一个 `FLAG_SECURE`，所以它今天也是关着的。那条归 M4。
>

## T-155 手动新增/编辑卡

**预估** 1.5 人日 · **依赖** T-153

**交付物** `feature:cardedit`：标题、商家名、颜色选择、码制选择、码值手输、备注（≤ 2000 字符）、`expires_on` 日期。

**实现要点**

**验收标准** 飞行模式下新增卡立即可见且带待同步徽章（J4 旅程）。

## T-157 从图片录入（Photo Picker）

**预估** 2 人日 · **依赖** T-156

**交付物** `feature:imageimport`：`PickVisualMedia(ImageOnly)` → 降采样解码 → ML Kit 静态图识别 → 0/1/多码分支。

**实现要点**
- **必须用 Photo Picker**，**不得**申请 `READ_MEDIA_IMAGES` / `READ_EXTERNAL_STORAGE`——用户只授予单张图片的临时访问，这让隐私声明可以写"我们无法访问你的相册"。
- **图片绝不落盘、绝不上传、绝不进日志**（含 Sentry 附件与面包屑）。这是 ADR-12（不做图片存储）与 ADR-13 能共存的唯一前提。解码后立即 `bitmap.recycle()`，不持有 Uri。
- **必须降采样**：`ImageDecoder + setTargetSampleSize`，长边 ≤ 2048 px。4000×3000 直接 Bitmap 化在 2 GB RAM 低端机上会 OOM。2048 px 既保证 1D 码最小模块宽 ≥ 2 px，又把内存控制在 ~16 MB。
- `InputImage.fromBitmap(bitmap, rotationDegrees = 0)`——ImageDecoder 已应用 EXIF 旋转，再传角度会转两次。
- 解码在 `Dispatchers.Default`，超过 5 秒视为失败。
- **必须复用与相机路径完全相同的** `BarcodeScanner` 实例与格式映射入口，**禁止为图片路径写第二套 `when` 分支**。
- 结果分支：0 个 → "未识别到条码" + `[换一张图片] [手动输入]`（**不做无意义的重试引导**）；1 个 → 直接进编辑页预填；≥2 个 → 在缩略图上按 `boundingBox` 画框让用户点选（按面积降序，最大的通常是主码）。
- SHOULD（可裁剪，见 README）：`ACTION_SEND` + `image/*` intent-filter，支持从其他 App 分享图片直达本流程。

**不做**：图片裁剪/旋转编辑器、批量导入、从 PDF 导入（§1.3 范围蔓延）。

**验收标准** §13.4-8 图片解码测试：单码图、多码图、无码图、4000×3000 超大图（不 OOM）、EXIF 旋转 90° 的图；断言与相机路径产出**相同**的 `BarcodeFormat` 与 `rawValue`。

**规格引用** §1.4 J1b、§7.3、§10.1、§13.4、ADR-13
