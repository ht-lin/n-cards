## T-101 Identity 数据模型与迁移

**预估** 1.5 人日 · **依赖** T-005

**交付物** `users` / `otp_challenges` / `devices` / `sessions` 四张表的 Doctrine 实体、仓储接口与迁移（DDL 见 §17.1）。

**实现要点**
- `users` **不存明文邮箱列**：`email_hash BYTEA UNIQUE`（HMAC-SHA256 + Vault pepper）用于查找，`email_encrypted TEXT`（Vault Transit）用于发信。
- `users.username TEXT UNIQUE NULL`——**可空是有意的**（首次 OTP 验证即建行，此时尚未设 username），不是遗漏。
- `otp_challenges.is_decoy BOOLEAN`：邮箱不存在时创建的哑挑战。
- `sessions.previous_token_hash` 为轮换重放检测预留。
- 所有表带 `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`；外键显式命名 `fk_<table>_<column>`。

**验收标准** 迁移 `up`/`down` 往返通过；`doctrine:schema:validate` 通过；集成测试断言 `email_hash` 唯一约束与 `username` 唯一（大小写不敏感，存归一化小写值）。

**规格引用** §5.2、§17.1

> ✅ **已交付，三条验收标准全部实测通过**（2026-09-05）。
> `composer migration:check` 三步全绿（up → down 往返 → `schema:validate`
> "The database schema is in sync with the mapping files"）；
> `doctrine:schema:update --dump-sql` 报 "Nothing to update"，即映射与迁移逐字一致。
> `composer qa` 1259 tests / 6588 assertions 全绿，集成用例 **0 skip**；
> 覆盖率整体 89.0%、`Module/Identity/Domain` 95.3%（门槛 85%）。
>
> **落地时冒出来的三条约束，合起来决定了全部实现形态**，详见
> [ADR-0011](../adr/0011-doctrine-orm-xml-mapping-and-module-owned-foreign-keys.md)：
> ① deptrac 的 `Identity.Domain: [Shared.Domain]` 让属性映射结构性不可行 → 映射是 XML；
> ② Doctrine 懒加载要继承实体并回填属性 → 实体不能 `final`、属性不能 `readonly`
> （这破了本仓库 `final readonly` 的惯例，是有据可查的例外）；
> ③ `schema:validate` 会把库里的外键与 ORM 元数据对账 → 外键必须建成 `<many-to-one>`，
> 而且索引、唯一约束与每个 `DEFAULT` 都要在 XML 里与迁移**逐字**重复一遍。
>
> **相对任务卡的三处增补**（都不是范围蔓延，理由随代码注释）：
> - 新增 `Shared\Domain\Crypto\HashDigest` + `HashDigestType` / `CiphertextType`
>   两个 DBAL 类型。六个 `BYTEA` 列若用裸 `string`，「hex 写进摘要列」与
>   「用 `===` 比摘要」都拦不住，而后者是 §7.1 明令要常量时间的地方。
>   T-109 的 `barcode_value_fingerprint` 直接复用。
> - 仓储除接口外**也交付了 Doctrine 实现**。没有实现的话 ORM 的读写路径在本任务里
>   从未真正执行，`schema:validate` 绿了也只证明映射语法对。
> - §17.1 补上了 `otp_challenges` / `devices` / `sessions` 的 DDL 片段
>   （原先只有 §5.2 的列表格）。
>
> ⚠️ **留给 T-109 的雷**：`cards.owner_id → users(id)` 是**跨模块**外键，
> 而按 ③ 它必须建成 ORM 关联才能让 `schema:validate` 通过 ——
> 但 `Wallet.Domain` 的 deptrac 允许列表里没有 `Identity.Domain`。
> 三条出路与各自的代价写在 ADR-0011 的「遗留问题」一节，T-101 刻意没有替它决定。

## T-102 邮件通道与双语模板

**预估** 1.5 人日 · **依赖** T-003（先决 Q3）

**交付物**
- `Notification` 模块的 `MailSenderInterface` + Symfony Mailer 实现（DSN 一行可切换通道）
- `templates/email/{de,en}/`：OTP 码、Magic Link、新设备登录提醒、refresh 重放安全提醒
- Messenger `email` transport（异步发送）+ `email_send_total` 指标（标签 `provider`/`template`/`result`）
- 全局日发信量阈值告警 + **自动熔断非关键邮件（保留 OTP）**
- SPF / DKIM / DMARC 配置（`p=quarantine` → `reject`）

**实现要点**
- §3.2 是**有意识的风险接受**：一期单通道、无双活、无送达率监控体系。前提是**把邮箱服务商细节完全收敛在 `MailSenderInterface` 之后**——这是"未来 2 人日能补回来"的唯一保证。业务代码不得出现任何服务商特有类型。
- 服务商必须满足：EU/EEA 处理 + 可签 AVV/DPA + 支持自定义域 SPF/DKIM。**不得**用个人/消费级邮箱或美国 SaaS 免费层（合规硬伤）。
- 外发邮件只有两类：OTP/Magic Link（收件人 = 请求者自己输入的邮箱）与安全提醒（收件人 = 账号自己）。**没有任何路径让用户指定第三方收件人**。

**验收标准** 上线前手工验证：向 Gmail / GMX / Web.de / Outlook 各发一封 OTP，确认不进垃圾箱（4 次手工验证，记录结果）。

**规格引用** §3.1、§3.2、§8.3、§14.4

## T-103 `POST /auth/otp/request`

**预估** 1.5 人日 · **依赖** T-101, T-102, T-006

**交付物** 端点实现 → **恒定** `202 {challenge_id, expires_at, resend_after_seconds: 60}`。

**实现要点（防枚举，逐条都是 MUST）**
- 邮箱**不存在**时同样创建 challenge（`is_decoy = true`）并返回一个哑 `challenge_id`，**不发信**；响应体与**耗时**与真实路径不可区分。
- 限流三维：email_hash 1/min、5/h、10/day；IP 20/h；全局熔断。
- 6 位码用 `random_int`（CSPRNG），存 `HMAC-SHA256(code, pepper)`，**不存明文**。
- 新建 challenge 时作废该 email 的旧 challenge（单次登录只允许一个活跃 challenge）。
- 有效期 10 分钟；`attempts` 上限 5。

**验收标准** 集成测试断言：已注册 vs 未注册邮箱的响应体结构、状态码、耗时分布不可区分；限流触发时返回 429 + `Retry-After`。

**规格引用** §3.8、§6.2、§6.3.1、§7.1、§7.5

## T-104 `POST /auth/otp/verify` + 注册 + JWT 签发

**预估** 2 人日 · **依赖** T-103

**交付物** 验证端点 → `200 {access_token, expires_in, refresh_token, user}`；首次验证成功即创建 `users` 行（注册）。

**实现要点**
- `hash_equals()` **常量时间**比较；`attempts++`，> 5 或过期 → 401；decoy → **恒 401 且耗时与真实路径相同**。
- 成功后：upsert user → 创建 `device`（客户端生成 id，安装级唯一）+ `session` → 签发 JWT（EdDSA Ed25519，claims `sub, sid, did, jti, iat, exp`，**15 分钟**）+ refresh（32 字节随机，Base64url，不透明，**90 天滑动**）→ 写 `audit_log(login_success)`。
- 新设备登录 → 向该用户所有既有设备发推送 + 向邮箱发提醒信（设备型号、大致时间、粗粒度地区）+ 信中"这不是我"的一键撤销链接（**同样走 POST 确认**）。
- `POST /auth/otp/verify` 限流：challenge_id 5 次总计；IP 60/h。

**验收标准** 单测覆盖常量时间比较与 decoy 路径；集成测试断言首次验证创建的 user 行 `username IS NULL`。

**规格引用** §6.3.1、§7.1、§7.5

## T-105 Refresh 轮换与重放检测、logout、设备管理

**预估** 2 人日 · **依赖** T-104

**交付物**
- `POST /auth/token/refresh`（轮换后的新令牌对）、`POST /auth/logout`
- `GET /v1/me/devices`（含当前设备标记）、`DELETE /v1/me/devices/{id}`（远程登出）、`PUT /v1/me/devices/{id}/push-token`

**实现要点**
- 每次刷新签发新 refresh token，旧 token **立即失效**，`previous_token_hash` 记录。
- 收到**已使用过的** refresh token → 判定令牌被窃：撤销该会话家族全部令牌 + `audit_log(reuse_detected)` + 告警 + 给用户发安全提醒邮件。
- 服务端**不做** access token 黑名单（15 分钟窗口可接受），但会话撤销后 refresh 立即失效。
- `revoked_reason` 取值：`logout` / `reuse_detected` / `user_revoked` / `account_deleted`。
- 限流：refresh 按 session 60/h。

**验收标准** 集成测试：重放旧 refresh token → 整个会话家族被撤销且发出提醒邮件；远程登出某设备后该设备的 refresh 立即失效。

**规格引用** §5.2、§7.1、§7.5

## T-106 Magic Link

**预估** 1 人日 · **依赖** T-104

**交付物** 邮件内 Magic Link → `https://app.n-cards.de/l/magic/*` 落地页 + `POST /v1/auth/magic/consume`；`assetlinks.json` 托管。

**实现要点（这是最容易实现错的一处）**
- 企业邮件安全网关（Microsoft Defender、Barracuda）会**自动 GET 邮件里的所有链接**。若 `GET` 即消费，用户还没点开就已失效。
- 因此：`GET` 只渲染"点击继续登录"按钮，**不消费令牌**；实际消费走 `POST`；对 `HEAD` 与预取（`Purpose: prefetch`）**不做任何状态变更**。
- App Links 域名下**只剩 Magic Link 一种用途**（好友邀请落地页已随 C2 整体删除），但 `assetlinks.json` 仍需保留。

**验收标准** 集成测试断言 `GET` 与 `HEAD` 不改变 `consumed_at`；`POST` 消费一次后重复 POST 返回 401。

**规格引用** §6.2、§7.1

## T-107 Username 值对象与一次性设定端点

**预估** 1.5 人日 · **依赖** T-104, T-006（先决 Q9）

**交付物** `Identity/Domain/ValueObject/Username.php` + `POST /v1/me/username`。

**实现要点**
- 字符集 `^[a-z0-9_]{3,20}$`；归一化 `trim` + `toLowerCase`，**必须用 `Locale.ROOT` 语义**（土耳其语的 `I→ı` 会破坏匹配）。
- 保留词黑名单（配置文件维护）：`admin`、`support`、`ncards`、`help`、`root`、`system`、`info`、`kontakt`、`datenschutz`，德语场景补 `impressum`、`hilfe`、`konto`（Q9）。
- **一次性写入**：已非空 → `409 username_immutable`。**不存在 PATCH/PUT 对应端点——不可变是靠"没有这个端点"保证的**。
- 唯一冲突 → `409 username_taken`（这是**有意为之**的枚举面：注册时必须告诉用户名字被占了，否则功能不可用）。
- 校验失败 → `422 username_invalid`。
- 限流：按 user **10 次总计**（成功一次后该端点永久 409）。

**验收标准** §13.4-6 的 username 不变性测试全绿：`Anna_B ` 与 `anna_b` 视为同一个且第二次返回 `username_taken`；保留词被拒；设定后 `POST` 与 `PATCH /v1/me`（含 `username` 字段）**均**返回 409（不静默忽略）。

**规格引用** §3.8、§5.2、§6.2、§7.5、§13.4

## T-109 Wallet：cards 模型与 CRUD

**预估** 2.5 人日 · **依赖** T-005, T-104

**交付物** `cards` 表 + `GET /v1/cards`（游标分页）、`POST /v1/cards`、`GET /v1/cards/{id}`、`PATCH /v1/cards/{id}`、`DELETE /v1/cards/{id}`。

**实现要点**
- **`sort_order` 与 `is_pinned` 不在 `cards` 上**（在 `card_members` 上，见 T-110）。这是共享模型的必然结果，最容易漏掉。
- `barcode_value_encrypted` / `note_encrypted` 走 Vault Transit；列表查询**必须**用 `BatchDecryptor` 一次批量解密（禁止循环调 Vault）。
- `barcode_value_fingerprint BYTEA`：HMAC(payload)，用于重复卡检测，不可逆。
- `encryption_scheme TEXT NOT NULL DEFAULT 'server_v1'`（为二期 E2EE 预留）。
- **创建幂等**：body 含客户端生成的 UUIDv7 `id`；`id` 已存在且属同一用户 → `200` + 现有实体；属他人 → `409 id_conflict`。
- **更新乐观锁**：`If-Match: "<revision>"`；匹配 → `revision += 1` + `200`；不匹配 → `409 {"code":"revision_conflict","current":{…}}`。
- **删除**：软删（`deleted_at`，90 天后硬删）+ 墓碑。
- 权限：`PATCH`/`DELETE` 对**非 owner 一律 `403 insufficient_role`**，即使请求体合法、revision 正确。

**验收标准** 契约测试全绿；集成测试覆盖幂等创建、revision 冲突、批量解密性能基准（200 张卡 bootstrap P95 ≤ 700 ms）。

**规格引用** §5.2、§5.3、§5.4.3、§6.2、§9.1

## T-150 令牌存储与网络认证层

**预估** 1.5 人日 · **依赖** T-009, T-010

**交付物** `data:auth` Repository + OkHttp `Authenticator`/`Interceptor`：附加 Bearer、401 `token_expired` → **静默刷新后重试一次**、401 `token_invalid` → 清空本地会话跳登录。

**实现要点**
- Access token 存内存 + `EncryptedSharedPreferences`；refresh token **仅存** `EncryptedSharedPreferences`。
- 刷新必须串行化（Mutex），避免并发 401 触发多次轮换——**轮换重放检测会把用户踢下线**。
- 错误映射对 `code` 分支，**不得解析 `detail`**。

**验收标准** 单测：并发 5 个 401 只触发一次刷新；`token_invalid` 会清空本地会话。

**规格引用** §6.1、§7.1、§7.3

## T-152 `core:barcode` 渲染与格式映射

**预估** 1.5 人日 · **依赖** T-008

**交付物** ZXing `MultiFormatWriter` → `BitMatrix` → Bitmap 渲染器 + **唯一**的 `BarcodeFormat` 枚举（ML Kit ↔ ZXing ↔ 展示名的映射集中在 `core:model`）。

**实现要点**
- **必须按目标 `View` 尺寸生成**（不要生成小图再放大——边缘模糊会导致扫码枪读不出）。
- **必须强制白底黑码**，无论 App 主题深浅。深色模式下的条码是扫码失败的经典原因。
- 1D 码 `margin` 至少 10 模块宽（静区），否则部分扫码枪拒读。
- 渲染在 `Dispatchers.Default`，结果缓存于内存 LruCache（key = format + value + size）。
- **禁止**在各处散落 `when` 做格式映射。
- 支持码制：EAN-13/8、UPC-A/E、Code 128/39/93、ITF、Codabar、QR、Aztec、PDF417、DataMatrix。

**验收标准** 单测覆盖全部码制的映射往返；真机上用扫码枪/另一台手机实测能读出 EAN-13 与 QR。

**规格引用** §1.3、§10.1

## T-157 从图片录入（Photo Picker）

**预估** 2 人日 · **依赖** T-156

**交付物** `feature:imageimport`：`PickVisualMedia(ImageOnly)` → 降采样解码 → ML Kit 静态图识别 → 0/1/多码分支。

**实现要点**
- **必须用 Photo Picker**，**不得**申请 `READ_MEDIA_IMAGES` / `READ_EXTERNAL_STORAGE`——用户只授予单张图片的临时访问，这让隐私声明可以写"我们无法访问你的相册"。
- **图片绝不落盘、绝不上传、绝不进日志**（含 Sentry 附件与面包屑）。这是 ADR-12（不做图片存储）与 ADR-13 能共存的唯一前提。解码后立即 `bitmap.recycle()`，不持有 Uri。
- **必须降采样**：`ImageDecoder + setTargetSampleSize`，长边 ≤ 2048 px。4000×3000 直接 Bitmap 化在 2 GB RAM 低端机上会 OOM。2048 px 既保证 1D 码最小模块宽 ≥ 2 px，又把内存控制在 ~16 MB。
- `InputImage.fromBitmap(bitmap, rotationDegrees = 0)`——ImageDecoder 已应用 EXIF 旋转，再传角度会转两次。
- 解码在 `Dispatchers.Default`，超过 5 秒视为失败。
- **必须复用与相机路径完全相同的** `BarcodeScanner` 实例与格式映射入口，**禁止为图片路径写第二套 `when` 分支**。
- 结果分支：0 个 → "未识别到条码" + `[换一张图片] [手动输入]`（**不做无意义的重试引导**）；1 个 → 直接进编辑页预填；≥2 个 → 在缩略图上按 `boundingBox` 画框让用户点选（按面积降序，最大的通常是主码）。
- SHOULD（可裁剪，见 README）：`ACTION_SEND` + `image/*` intent-filter，支持从其他 App 分享图片直达本流程。

**不做**：图片裁剪/旋转编辑器、批量导入、从 PDF 导入（§1.3 范围蔓延）。

**验收标准** §13.4-8 图片解码测试：单码图、多码图、无码图、4000×3000 超大图（不 OOM）、EXIF 旋转 90° 的图；断言与相机路径产出**相同**的 `BarcodeFormat` 与 `rawValue`。

**规格引用** §1.4 J1b、§7.3、§10.1、§13.4、ADR-13
