## T-002 后端 Symfony 骨架与质量门禁

**角色** BE · **预估** 1 人日 · **依赖** T-001

**交付物**
- Symfony 7.x / PHP 8.3+ 骨架，目录严格按 §12.2：`src/Shared/{Domain,Application,Infrastructure,Http}`、`src/Module/{Identity,Wallet,Sharing,Social,Sync,Notification,Compliance}` 的空壳
- `phpstan.neon`（level **8**，`src/` 全量）、`.php-cs-fixer.dist.php`（`@Symfony` + `@PHP83Migration`）、`phpunit.xml.dist`
- `deptrac.yaml`：按 §4.2 的 5 条规则配置层与模块边界

**实现要点**
- Deptrac 必须同时强制**两个维度**：① 模块间（不得引用他模块的 `Domain`/`Infrastructure`，只能经 `Application\Port\*`）；② 层间（`Http → Application → Domain`，`Domain` 不得 import 任何框架类型）。
- 为 `Sync\Infrastructure\Doctrine\SyncReadModel` 预留显式豁免槽位并加注释说明（唯一允许的跨模块只读查询入口）。
- 覆盖率阈值先配上：整体 ≥ 70%，`Module/*/Domain` 与 `Application` ≥ 85%（此刻还没代码，配置先就位）。

**验收标准** `phpstan`/`cs-fixer`/`deptrac` 三件套本地与 CI 均可跑；故意写一个跨模块 `Domain` 引用能让 deptrac 报 violation。

**规格引用** §4.2、§12.2、§13.3

## T-004 Shared 内核（HTTP 横切层）

**角色** BE · **预估** 1.5 人日 · **依赖** T-002

**交付物**
- `Shared/Domain`：`Uuid`（UUIDv7 生成与校验）、`Clock`、`DomainEvent`、`DomainException`
- `Shared/Application`：`CommandBusInterface`、`EventBusInterface`
- `Shared/Infrastructure/Http`：
  - `ApiProblemExceptionListener` → RFC 9457 Problem Details（含 `code`、`request_id`、`errors[]`、`current`）
  - `RequestIdListener`（`X-Request-Id` 透传/生成，写入所有日志）
  - `ClientVersionListener`（解析 `X-Client: android/1.4.0 (26)`，缺失即 400）
  - `IdempotencyMiddleware`（`Idempotency-Key` header，Redis 存 24h，覆盖所有 POST）
- `Shared/Http`：`AbstractApiController`、`CursorPaginator`（游标式，默认 50 / 最大 200，**禁止 offset**）
- `Shared/Infrastructure/Doctrine`：`UuidType`、`TransactionalRunner`

**实现要点**
- ⚠️ **`ClientVersionListener` 必须把 `/health/*` 排除在外**。T-003 已交付的
  `/health/live` 与 `/health/ready` 的调用方是 Docker healthcheck、Caddy 与
  §14.3 部署流程里的 Ansible，它们**不带** `X-Client`。漏掉这条豁免，两个探活
  端点会在本任务合入当天集体变 400，连带 compose 起栈与 staging 部署的健康检查
  一起失效。同样的豁免逻辑将来还要覆盖 T-007 之后的任何非 `/v1` 端点。
- §6.1 的**统一错误码表**要落成一个 PHP enum（`validation_failed` / `token_expired` / `insufficient_role` / `username_required` / `revision_conflict` / `full_resync_required` / `username_taken` / `username_immutable` / `limit_exceeded` / `client_too_old` / `rate_limited` …），客户端只对 `code` 分支。
- `detail` 只写英文开发者文案，**服务端绝不返回可展示的德语文案**。

**验收标准** 单测覆盖每个错误码的响应形状；契约测试能对 Problem Details schema 校验通过。

**规格引用** §6.1、§12.2

## T-005 Vault Transit 与加密门面

**角色** BE · **预估** 2 人日 · **依赖** T-003（Q6 需先决策）

**交付物**
- Vault 初始化脚本：`transit/ncards-card`、`transit/ncards-pii`（AES-256-GCM96）、`transit/ncards-hmac`（HMAC-SHA256，**不轮换**）、JWT 签名密钥存 KV
- AppRole 认证（policy 最小化：仅对指定 key 的 `encrypt|decrypt|rewrap`；**不授予** `keys/*`、`rotate`、`rewrap` 管理权），token TTL 1h 自动续期
- `Shared/Infrastructure/Crypto`：`CryptoServiceInterface`、`VaultTransitCrypto`、`HmacHasher`、`BatchDecryptor`
- `infra/vault/` 策略文件（§17.4）+ `docs/runbooks/vault-unseal.md` 初版

**实现要点**
- **批量解密是硬要求**：`BatchDecryptor` 用 Transit 的 `batch_input`，**禁止在循环里逐条调 Vault**。目标 200 条 P95 < 80 ms。
- **不缓存明文**。若压测不达标，只允许单个 HTTP 请求生命周期内的进程内 memo，请求结束即销毁。
- auto-unseal **关闭**，unseal key（Shamir 3-of-5）离线保管，**绝不进 CI**。

**验收标准** 集成测试（真实 Vault 容器）：加密→解密往返一致；200 条 batch decrypt 有基准测试并记录耗时；deptrac 确认无模块直接 import `VaultTransitCrypto`（只经接口）。

**规格引用** §3.3、§5.3、§7.4、§17.4

## T-006 限额与限流基础设施

**角色** BE · **预估** 1 人日 · **依赖** T-003, T-004

**交付物**
- `config/packages/ncards_limits.yaml`：§7.5 全部限额常量（卡数 500、每卡成员 20、好友 500、payload 1024 B、note 2000 字符、title 100 字符、username 3–20、好友请求 50/日、共享邀请 100/日）
- `Shared/Infrastructure/RateLimit/LimitEnforcer`：超限抛出 `422 limit_exceeded`
- `config/packages/rate_limiter.yaml`：Symfony RateLimiter + Redis 滑动窗口，按 §7.5 速率表配置（端点 × 维度）
- 限流响应**必须**带 `Retry-After` 与 `X-RateLimit-Remaining`；多维度同时触发时返回**更长的** `Retry-After`

**实现要点** 明确区分两类：**系统限额**（超限 → `422 limit_exceeded`）与**速率限制**（超限 → `429 rate_limited`）。不建 `plan`/`quota` 表（ADR-11）。

- 复用 T-004 已交付的三样东西，**不要另起炉灶**：
  `Shared\Infrastructure\Redis\RedisConnectionFactory`（全仓库唯一的 Redis 连接构造点）、
  `Shared\Domain\Http\ApiSurface`（只对 `/v1/*` 生效的正向白名单）、
  `Shared\Domain\Error\ErrorCode`（`limit_exceeded` / `rate_limited` 都已在表里）。
- ⚠️ **Redis 不可用时限流必须 fail-CLOSED**，与 T-004 的幂等**相反**（那个是 fail-open）。
  限流 fail-open 等于在故障期间关掉 §7.5 的 OTP 与 username 枚举防线 ——
  那是安全控制，不是便利功能。这个不对称是刻意的，理由见 ADR-0003；
  在代码里也要注释引用，否则 reviewer 会当成不一致顺手「修」掉。
- ⚠️ 按 IP 的限流依赖 `framework.trusted_proxies`（T-004 已配）。真要确认它还在生效，
  看 `tests/Api/TrustedProxyTest` —— 那条没了的话，§7.5 的 IP 20/h 会把全世界算作一个 IP。

**验收标准** 单测覆盖每个限额常量的边界值；限流集成测试验证滑动窗口与 header。

**规格引用** §3.1、§7.5

## T-007 OpenAPI 契约底座与 Spectral

**角色** 全员 · **预估** 1 人日 · **依赖** T-001

**交付物**
- `docs/api/openapi.yaml`（OpenAPI **3.1**）v0：Auth + Cards 端点骨架 + 通用组件（Problem Details、Cursor 分页参数、`X-Client` header）
- Spectral 自定义规则集：必须有 `operationId`、必须有错误响应、必须有示例、所有 schema `additionalProperties: true`
- 后端契约测试底座：`tests/Api` + `league/openapi-psr7-validator`

**⚠️ 与 T-004 的衔接**
- `components/schemas/Problem` 必须用 `$ref` **指向** T-004 已交付的
  `docs/api/schemas/problem-details.schema.json`，**不要复制一份** —— 两份 `code`
  枚举必然会漂，而 Android 的 `ApiError` 是照它生成的。
- 契约里的 `code` 枚举与 `App\Shared\Domain\Error\ErrorCode` 的一致性已由
  `tests/Unit/Shared/Domain/Error/ProblemDetailsSchemaTest` 逐项断言，沿用即可。
- 通用组件里的 Cursor 分页参数用 T-004 已定的信封：`items` / `next_cursor` / `has_more`
  （见 `docs/api/README.md`）。
- `X-Client` header 的格式与 `Idempotency-Key` / `Idempotency-Replayed` 两个 header
  也要进契约 —— 后者是 T-004 自定义的，标准里没有。

**实现要点** **禁止**用 API Platform / NelmioApiDocBundle 从实现生成契约——方向反了，会让契约跟着实现漂移。

- ⚠️ **`league/openapi-psr7-validator` 的 README 明写只支持 OpenAPI 3.0.x，但它能跑 3.1**。
  0.23 起底层解析器从 `cebe/php-openapi` 换成了支持 3.1 的
  `devizzent/cebe-php-openapi`，文档没跟上而已。落地前先花半小时实测四件事
  （3.1 版本号、跨文件 `$ref`、`type: [string, "null"]`、坏响应确实抛异常）——
  四条全过才动手写契约。**结论：0.24 四条全过**，另需 `symfony/psr-http-message-bridge`
  + `nyholm/psr7` 把 Symfony 的 `Response` 转成 PSR-7。
  - ⚠️ `nyholm/psr7` 的 Symfony recipe 会生成
    `config/packages/nyholm_psr7.yaml`，把 PSR-17 服务注册进**生产**容器 ——
    而它是 `require-dev`。**必须删掉那个文件**，否则 `composer install --no-dev`
    之后容器编译会找不到类。契约测试自己 `new Psr17Factory()` 就够了。

- ⚠️ **`servers[].url` 带 `/v1`，所以 `paths` 下不带**（§6.1 的基址、§17.2 的参考片段
  都是这个形态），而后端路由是 `/v1/cards`。这个落差由校验器的 `PathFinder` 自动消化，
  但**三处必须同时对**：servers 带、paths 不带、测试传真实路径。
  `OpenApiDocumentTest::testServersCarryTheVersionPrefixAndPathsDoNot()` 钉着前两处。

- **契约首版只写 Auth + Cards**，其余 §6.2 端点由各自的任务在「先改契约」时补入。
  提前把 schema 全摆好只会得到一堆没人对照实现校对过的定义 ——
  连 §17.2 里的 `PublicUser` 都没放进去（它属于 T-302 的 `/users/lookup`）。

- **验收标准的后半条不要靠真实端点来满足**。契约里的十个端点一个都还没实现
  （Auth 是 T-103/104，Cards 是 T-109），但「校验器会咬人」必须**当天**就被证明，
  否则中间三个任务都是在没有契约门禁的情况下写的。做法是拿契约**自己的 `example`**
  当夹具：正向全过、改坏必拒。顺带把 `example` 从文档装饰变成了可执行断言。
  **不要**另建 `tests/Fixture/Contract/*.json` —— 那是第二个真相源，必然会漂。

- ⚠️ **`.github/workflows/backend.yml` 的 `paths` 过滤要补 `docs/api/**`**。
  契约文件在 `docs/` 下、校验它的测试在 `backend/` 下，不补的话「只改 openapi.yaml」

## T-008 Android 工程骨架与 Convention Plugins

**角色** AND · **预估** 1.5 人日 · **依赖** T-001

**交付物**
- `android/` 按 §12.3 建模块：`app`、`core/{model,common,designsystem,ui,database,datastore,crypto,network,barcode,testing}`、`data/{auth,card,friend,sharing,sync}`、`sync`、`feature/*`、`widget`、`benchmark`（先建空模块）
- `gradle/libs.versions.toml`（**唯一**依赖声明处）
- `build-logic/convention/`：`ncards.android.{application,library,feature,hilt,room}`、`ncards.kotlin.serialization`
- `core:designsystem`：Material 3 Theme、Color tokens、Typography
- `ktlint` + `detekt` + Android Lint 配置（`HardcodedText`、`MissingTranslation`、`ContentDescription` 提升为 **error**）
- `minSdk 26`，德语为**默认** `values/`，英语为 `values-en/`

**实现要点** Gradle 强制模块依赖规则：`app → feature:* → data:* → core:*`；`feature:*` **之间禁止互相依赖**；`core:*` 不得依赖 `data:*`/`feature:*`；`sync` 不得被 `feature:*` 直接依赖。

**验收标准** `assembleDebug` 成功；故意在两个 feature 间加依赖会构建失败；德语为默认资源目录。

**规格引用** §4.3、§11.1、§12.3、§13.3

**交付产物（落地后）**

- 工具链：AGP **9.3.2** / Gradle **9.7.1** / Kotlin **2.4.10** / KSP 2.3.11，
  `compileSdk 37`（minor 1）· `targetSdk 36` · `minSdk 26`。
  wrapper 带 `distributionSha256Sum`。
- `android/gradle/libs.versions.toml`：唯一依赖声明处，只声明**已在用**的坐标，
  每条注明归属任务。
- `build-logic/convention/`：任务书点名的六个插件 + 四个内部插件
  （`ncards.module.graph` / `ncards.quality` / `ncards.android.compose` /
  `ncards.jvm.library`），每个的存在理由写在实现类头部。
- §12.3 的 30 个模块全建；`app` 与 `core:designsystem` 有实质内容，其余空壳。
- `.github/workflows/android.yml`（最小版，T-011 并进三条并行流水线）。

**⚠️ 三个 AGP 9 的坑**（写任何 convention plugin 之前先读 `android/README.md` 的同名段）

1. **不要应用 `org.jetbrains.kotlin.android`** —— AGP 9 自带 Kotlin 支持，应用它会被
   直接拒绝。jvmTarget 由 `compileOptions` 推导（已验证产物 class file major 61）。
2. **`CommonExtension` 不再带类型参数** —— AGP 8 的 `CommonExtension<*, *, *, *, *, *>`
   编译不过。
3. **不要写 `extension.apply { … }`** —— 它会绑到 `ExtensionAware` 的 Gradle 重载而非
   Kotlin 作用域函数，块内成员集体变成 "Unresolved reference"，报错完全不指向原因。

**⚠️ §13.3 点名的 `HardcodedText` 对本项目是空转的**

三条 lint 规则都按要求提升为 error 了，但按验收标准做反向验证时发现：
`HardcodedText` 检查的是 **XML 布局属性**（`android:text="…"`），而 §4.3 的选型是
「全 Compose，**无 XML 布局**」—— 往 `MainActivity` 里塞一个 `Text("hardcoded")`
再跑 `:app:lintDebug`，**结果是 BUILD SUCCESSFUL**。一条永远不会响的门禁比没有门禁
更糟，因为它让人以为这件事有人管着。

补法：`./gradlew checkComposeHardcodedText`（`build-logic` 的 `ComposeHardcodedText.kt`）。
`lint.xml` 里那三条**保留** —— Glance widget（T-254）与 RemoteViews 仍是 XML。
`ContentDescription` 有同样的局限，但 Compose 侧 Material3 把它做成了必填参数，
由编译器保证「有没有传」；「该给说明的图标传了 null」只能人工评审（T-452）。

## T-009 Room + SQLCipher 与 core:crypto

**角色** AND · **预估** 2 人日 · **依赖** T-008

**交付物**
- `core:crypto`：32 字节随机 passphrase → Android Keystore AES-GCM 包裹 → 存 `EncryptedSharedPreferences`；`DbPassphraseProvider`
- `core:database`：Room + `net.zetetic:sqlcipher-android`，`cards` / `card_members` / `sync_outbox` / `sync_meta` 等表的初版 entity 与 DAO
- `AndroidManifest`：`android:allowBackup="false"`、`dataExtractionRules` 排除全部数据
- `networkSecurityConfig`：`cleartextTrafficPermitted="false"`

**实现要点**
- Keystore 密钥**不得**设 `setUserAuthenticationRequired(true)`——Widget 与 FCM 后台同步需要在无用户交互时读写数据库。此取舍写入代码注释并链接 §3.4。
- 令牌只存 `EncryptedSharedPreferences`，**绝不**明文写 SharedPreferences 或 Room。
- 生物识别应用锁只锁 UI，**不锁数据库**（M4 的 T-450 实现 UI 部分，此处只留接口）。

**交付产物（落地后）**

- `core:crypto`：`KeyWrapper`/`KeystoreAesGcmKeyWrapper`（AndroidKeyStore 的
  AES-256-GCM，别名 `ncards_db_master_v1`，密文 `[版本][12B IV][密文||tag]`）、
  `SecretStore`/`KeystoreSecretStore`、`DbPassphraseProvider` + `Passphrase`、
  `CryptoModule`（全 `@Binds`，实现一律 `internal`）。
- `core:database`：四张表的 entity + DAO、`NcardsDatabase`（version 1，schema JSON 入库）、
  `SqlCipher`、`DatabaseModule`；`WalletCard` 投影。
- `:app`：`allowBackup="false"` + `res/xml/data_extraction_rules.xml`（`cloud-backup`
  **与** `device-transfer` 两段全排除）+ `res/xml/network_security_config.xml`。
- 测试：`core:crypto` 7 个单测（首次 / 复用 / 恢复三条分支）+ 14 个仪器测试
  （真 Keystore 上的往返、IV 不重复、篡改/截断/换密钥必须失败、
  `isUserAuthenticationRequired == false`、passphrase 持久化与恢复）；
  `core:database` 17 个仪器测试（三条验收标准 + 四张表的 DAO 行为）。

**三处与任务书字面的偏差，都有记录**

1. **不引入 `androidx.security:security-crypto`**（[ADR-0007](../adr/0007-android-secret-storage-without-jetpack-security.md)）：

   游标存 Proto DataStore；而 §5.4.3 的字段级三路合并需要 base 落盘才能跨进程重启
   存活。两者不重叠。
3. **`cards` 上没有 `sync_state` 列**，由 `sync_outbox` 派生（`CardDao.observeWallet`）。
   一份状态存两处迟早漂移成两份，而漂移时没人知道该信哪个。

**四张表以外的没建**：`friendships` / `share_invitations` 是 M3（T-301+），
`users` 要等 T-107 的 username —— 现在建等于凭空猜列，而 §13.5 的 expand–contract
意味着猜错要付迁移代价。

## T-010 core:network 与代码生成打通

**角色** AND · **预估** 1 人日 · **依赖** T-007, T-008

**交付物**
- `core:network:api`：`openapi-generator`（`kotlin` + `retrofit2` + `kotlinx-serialization`）产物，**提交入库但禁止手改**
- `core:network:impl`：OkHttp 配置、`X-Client` / `X-Request-Id` 拦截器、错误映射（HTTP + `code` → sealed `ApiError`）、重试策略
- Gradle task：重新生成并 diff，不一致即失败

**实现要点** `Json { ignoreUnknownKeys = true }` 是**硬要求**（前向兼容）；未知枚举值必须有 `UNKNOWN` 兜底分支，在生成器配置中保证。

**验收标准** 改动 `openapi.yaml` 后不重新生成 → CI 失败；`ApiError` 覆盖 §6.1 错误码表全部条目。

**规格引用** §3.10、§13.1、§13.6

**交付产物（落地后）**

- **`core:network:api`**：36 个文件的 `openapi-generator` 7.25.0 产物（`kotlin` +
  `jvm-retrofit2` + `kotlinx_serialization`），落在 `generated/` 下并提交入库。
  `AuthApi`（5 个 operation）/ `CardsApi`（6 个）+ 17 个 model + `infrastructure/`
  的序列化 adapter。方法名取自 `operationId`，与契约逐一对应。
- **build-logic 的 `ncards.openapi`**（第 11 个 convention plugin）：四个任务 ——
  `prepareOpenApiGeneratorInput` / `generateApiClient` /
  `generateApiClientForVerification` / `checkApiClientUpToDate`（挂在 `check` 上）。
  手写 `JavaExec` 而不是用 `org.openapi.generator` 插件，理由是配置缓存
  （仓库全局开着，赌第三方插件的兼容性没有退路）。
- **`core:network:impl`**：`NetworkConfig`、`ClientHeaderInterceptor` /
  `RequestIdInterceptor` / `RetryInterceptor`、`ApiError`（26 个 code 一码一类型 +
  3 个传输层）、`FieldError`（9 项词表 + `UNKNOWN`）、`ApiErrorMapper`、
  `ApiResult` + `execute {}`、`NetworkModule`；`AndroidManifest` 声明 `INTERNET`。
- **`:app`**：`AppNetworkModule` 绑 `NetworkConfig`（`BuildConfig.API_BASE_URL` 按
  buildType，debug → staging；`X-Client` 由 `VERSION_NAME` / `VERSION_CODE` 拼出）。
- **CI**：`android.yml` 的 `paths` 加 `docs/api/**`（否则只改契约的 PR 跑不到 diff
  检查，验收标准第 1 条落空），新增一步 `checkApiClientUpToDate`。
- **测试**：`core:network:impl` 36 个单测（错误码全覆盖、problem 映射与四个响应头、
  重试边界 9 条、`ignoreUnknownKeys` 与未知枚举兜底、`NetworkConfig` 校验）。

**验收标准的落实方式**

1. 「改 `openapi.yaml` 不重新生成 → CI 失败」：`checkApiClientUpToDate` 把契约重新
   生成到 `build/` 再与 `generated/` **逐文件比对**（不是 `git diff` —— 后者把
   「产物过期」和「工作区本来就脏」混成同一种失败）。实测：往 `CardPlacement` 加一个
   可选字段 → 该任务红并点名 `CardPlacement.kt`；还原后转绿。
2. 「`ApiError` 覆盖 §6.1 全表」：`Problem.toApiError` 是一个**没有 `else` 的
   `when`**，直接 `when` 生成的 `Problem.Code`。契约新增一个 code → 重新生成 →
   枚举多一项 → 那个 `when` 不再穷举 → **编译失败**。这比运行时断言早，
   也是本任务作为 §6.1 错误码表「第四方」的钉法。`ApiErrorCoverageTest`
   再补一层：两个 code 映射到同一类型（复制粘贴漏改）也会红。

**四处与任务书字面的偏差，都有记录**

1. **契约补了一行 `info.license.identifier`。** `openapi-generator` 的 spec 校验器
   把 OAS 3.1 里**可选**的 `identifier` 当必填，不写就 `Error count: 1` 直接中止。
   出路是 `--skip-validate-spec`（会连同「$ref 指不到」这类真问题一起关掉）或者补上
   这一行。选后者：它是纯元数据，§13.6 的禁止项一条不沾。
   `npm run lint:api` 与 `backend/tests/Api`（264 个）都仍然绿。
2. **给生成器派生了一份剥掉 `additionalProperties: true` 的契约副本**
   （`build/openapi-input/openapi.json`，不入库）。§13.1 第 5 条要求所有 schema 都
   `additionalProperties: true`，而生成器把「有 properties **又**有
   additionalProperties」的 schema 当成 Map，后果是 15 个模型全部继承一个语法非法的
   `HashMap<String, Any>()()`、嵌套模型被打上 `@Contextual`。生成器侧没有开关。
   **契约一个字都没动** —— 这正是 `docs/api/README.md` 结尾预留的那条出路的形态。
   只剥同时声明了 `properties` 的那些：`Problem.current` / `debug` 是真的自由形态
   对象，剥了会从 `Map<String, JsonElement>` 退化成裸 `Any`。
3. **覆写了两个 mustache 模板各一行**（`data_class_{req,opt}_var.mustache` 的
   `{{^isEnumRef}}`）。`$ref` 出去的枚举（`BarcodeFormat` / `CardRole`）会被上游模板
   误判成「需要外部序列化器」而加 `@Contextual`，运行时报
   `Serializer for class 'BarcodeFormat' is not found`。未改动的上游原文一并入库，
   `diff` 应当只有一行差异 —— 见 `core/network/api/templates/README.md`。
4. **跨文件 `$ref` 不需要 bundle。** T-007 留的那条「解不开就加
   `npm run bundle:api`」的预案**没有用上**：`openapi-generator` 7.25.0 能解
   `components/schemas/Problem` → `./schemas/problem-details.schema.json`，
   26 个 `code` 全部解出来。三个消费者至此都验过了。

**留给后续任务的五条**

- **T-011**（已结）：`koverVerify` 已打开。`:core:network:api` 的豁免保留，

- **`android/README.md` 说「`core:crypto` 没有这个问题」—— 那句话是错的。** 实测
  27.2%：`KeystoreAesGcmKeyWrapper` / `KeystoreSecretStore` 要真的 AndroidKeyStore，
  14 个测试全在 `androidTest`。它与 `core:database` 是同一个问题，拿同一条豁免。

比豁免更要紧的是**分母**：Dagger/Hilt 的生成代码原本整个计进来，把
`:core:network:impl` 摁在 64.5%（手写的 `RetryInterceptor` 其实是 32/33）。
`Coverage.kt` 现在排除生成代码，该模块随即过线。**四条豁免**（`network:api` /
`database` / `crypto` / `designsystem`）逐条写了理由。

> ⚠️ `core:crypto` 与 `core:database` 选豁免而不是并入仪器测试覆盖率，是因为后者要求
> PR 流水线里起模拟器，会把 12 分钟预算直接冲掉。**这个取舍应在 M1 重新评估** ——
> 那时 `data:*` 有了真实代码，覆盖率的分母才有代表性。

**仪器测试：api 26 这一档第一次跑通**

T-009 的 31 个测试此前只在 api 34 上验过。T-011 在本地 GMD 上跑了两档
（crypto 14 + database 17，共 62 次）**全绿** —— Keystore 与 SQLCipher 在
Android 8.0 上与 api 34 没有行为差异，`minSdk` 这一档的风险到此关闭。

配置上踩到三个坑，都写进了 `ManagedDevices.kt` 与 `gradle.properties`：
AGP 默认拒绝 API ≤ 26（要 `allowOldApiLevelDevices`）；`testedAbi` 必须显式写
`x86_64`（AGP 10 会改默认，而 x86_64 镜像不支持 NDK translation）；
两个模块 × 两档设备会起**四台**模拟器，16 GB 机器上会把 Gradle daemon 挤死
（`maxConcurrentDevices=1`）。

**留给后续任务的三条**

- **T-012**：`main.yml` 末尾的 `deploy-staging` 注释块。需要 Ansible playbook 与部署
  SSH key。⚠️ Vault unseal key 绝不进 CI（§14.3 / [ADR-0004](../adr/0004-manual-vault-unseal.md)）。
- **T-456**：`play-internal` 注释块 + release 变体的 `signingConfig`。
- **加新流水线的人**：必须同时加进 `pr.yml` 里 `pr-gate` 的 `needs`。不加，它红了
  PR 照样能合 —— 这是 ADR-0008 记的唯一失效模式。

## T-012 Hetzner staging + Ansible 自动部署

**角色** OPS/BE · **预估** 2 人日 · **依赖** T-003, T-011（Q1 需先决策）

**交付物**
- Hetzner（Nürnberg）CCX23 主机；`infra/ansible/` playbook（含 SSH 加固：仅密钥、禁 root、`fail2ban`、非 22 端口）
- Caddy 自动 TLS + 安全响应头：HSTS `max-age=63072000; includeSubDomains; preload`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`X-Frame-Options: DENY`、`CSP: default-src 'none'`
- `api.staging.n-cards.de` 部署 hello world，`main` 合入自动部署
- `sops`（age）加密的生产/staging 配置随 Ansible 下发；`.env` 不入库
- 生产发布流水线骨架：手动触发 + approval → 前置数据库快照 → 滚动重启 → 迁移 → 健康检查 → 失败自动回滚上一镜像 tag

**实现要点** staging **只用合成数据**，严禁复制生产数据（哪怕脱敏）。Vault unseal key 绝不进 CI/Ansible secrets。

**验收标准** 一次 `main` 合入能自动部署到 staging 并通过冒烟测试；`curl -I` 能看到全部安全头；`X-Powered-By`/`Server` 版本回显已禁用。

**规格引用** §7.4、§14.1、§14.2、§14.3
