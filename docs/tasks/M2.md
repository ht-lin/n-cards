## T-201 `change_log` 与 `ChangeLogSubscriber`

**预估** 2.5 人日 · **依赖** T-109, T-110

> **这是全项目最容易写错、且错了会在数据库层面泄露数据的任务。** 实现前请完整读完 §5.2 的 change_log 小节。

**交付物**
```sql
CREATE TABLE change_log (
  seq         BIGSERIAL PRIMARY KEY,
  entity_type TEXT        NOT NULL,   -- card | card_member | friendship | share_invitation | user_profile
  entity_id   UUID        NOT NULL,
  op          TEXT        NOT NULL,   -- upsert | delete
  audience    UUID[]      NOT NULL,
  occurred_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);
CREATE INDEX idx_change_log_audience ON change_log USING GIN (audience);
CREATE INDEX idx_change_log_seq_time ON change_log (seq, occurred_at);
```
+ `Shared/Infrastructure/Doctrine/ChangeLogSubscriber`。

**实现要点（每条都是 MUST）**
1. 任何对 `cards` / `card_members` / `friendships` / `share_invitations` 的写入，**必须在同一数据库事务内**写入对应 change_log 行。**由 Subscriber 统一处理，禁止业务代码手动拼装。**
2. **audience 的两条规则不对称，这是有意的，不是笔误**：
   - `card` 变更 → **广播**：该卡当前所有 `left_at IS NULL` 的成员（owner + 全部 viewer）。
   - `card_member` 新增/移除 → **点对点**：**仅 `[owner, 当事人]`**，**绝不含其他 viewer**。
   - **必须为这两类实体分别实现 audience 计算函数**，**不得**图省事复用同一个"取该卡全部成员"的函数——那正是泄露 viewer 名单的方式，而且泄露发生在数据库里，任何前端修补都无法挽回（T21）。
3. **删除类记录的 audience 必须取删除前的成员快照**。若先删 `card_members` 再算 audience，viewer 将**永远收不到墓碑**，卡会永久残留在他们本地库里。把"先快照 audience，再执行删除"固化在 Subscriber 里，不要留给业务代码。
4. `friendship` → audience 为双方。

**验收标准（§13.4-4 change_log audience 测试）**
- 成员加入/移除后，正确的用户收到 upsert / tombstone；
- owner 删卡 / 删号时 audience 取自**删除前快照**，viewer 端确实收到卡墓碑；
- 一张卡有 owner + 3 个互不为好友的 viewer 时，新增第 4 个 viewer 的 change_log audience 只含 `[owner, 该成员]`，前 3 个 viewer 的同步结果中**不出现**任何与他人相关的 `card_members` 行。

**规格引用** §5.2、§7.2 T21、§13.4

## T-202 `GET /v1/sync`（增量）

**预估** 2 人日 · **依赖** T-201

**交付物** 游标式增量同步端点，响应结构见 §5.4.2。

**实现要点**
- 游标 = base64url 的 `{"seq": 123456, "sv": 1}`（`sv` = schema_version）。
- **2 秒稳定窗口是必需的**：`BIGSERIAL` 在并发事务下可能"较小的 seq 后提交"，直接按 seq 推进游标会漏读。查询加 `AND occurred_at < now() - INTERVAL '2 seconds'`。代价是同步延迟固定 +≤2 s（在 10 s SLO 内可接受）。
- **去重折叠**：同一 `entity_id` 在窗口内多次变更 → 只返回该实体**当前状态**一次（按最大 seq 折叠）。游标推进到本批最大 seq。
- **`full_resync_required`（409）触发条件**：`since_seq` < change_log 最小 seq（超出 90 天保留期）；客户端 `sv` 不兼容；服务端检测到该用户的 change_log 有过清理/修复。
- `card_members` 由 audience **天然裁剪**——不需要额外过滤逻辑，但必须有测试证明它确实裁剪了（T-201 已保证 audience 正确）。
- `users` 只下发**好友与共享卡 owner 的最小资料**：`{id, username}` 两个字段。
- 限流：按 device 60/min；`limit` 上限 200。
- 性能预算：增量 0–50 条 P95 ≤ 250 ms。

**验收标准** 契约测试 + 并发写入下不漏读的集成测试（构造两个事务乱序提交）；`sync_changes_returned` histogram 指标已埋点。

**规格引用** §5.4.1、§5.4.2、§7.5、§9.1、§14.4

## T-203 `GET /v1/sync/bootstrap`（全量）

**预估** 1 人日 · **依赖** T-201

**交付物** 全量初始快照（cards + card_members + friendships + share_invitations + users 最小资料）+ 起始游标，用于首次登录与 `full_resync`。

**实现要点**
- 起始游标必须取**快照那一刻**的 seq 水位（同样考虑 2 秒稳定窗口），否则会漏掉快照期间的变更。

- 性能预算：200 张卡 P95 ≤ 700 ms（依赖 T-005 的 batch decrypt）。

**验收标准** 断言 viewer 的 bootstrap 结果中**每张共享卡恰好 2 行 `card_members`**，且卡实体无 `member_count`。

**规格引用** §4.2、§5.2、§5.4、§6.2、§9.1

## T-250 SyncEngine 核心

**预估** 3 人日 · **依赖** T-202, T-153

**交付物** `sync/` 模块：`SyncEngine.sync()` — 拉取增量 → 写入 Room（事务）→ 持久化游标。

**实现要点**
- **所有触发必须汇聚到同一个 `SyncEngine.sync()`**，由 `Mutex` 保证同一时刻只有一次同步在跑，**重入者等待并复用结果**（不是排队再跑一次）。
- 游标存 Proto DataStore。**分页各批独立提交 Room 事务**（避免大事务），但**游标只在每批成功写入后才持久化**——保证崩溃后从上一批续传，最坏情况是重放（幂等 upsert，安全）。
- `has_more = true` 时必须立即用 `next_cursor` 继续拉，直到 `false`。
- 下行写入必须处理墓碑：`card_tombstones` → 物理删除本地行；`member_tombstones` → 删成员行。
- **viewer 侧是纯消费者**：对共享卡只做下行写入 Room，**永远不为共享卡产生上行 outbox 记录**（`placement` 除外）。
- 目标延迟：Anna 保存 → Bob 前台可见 P95 ≤ 10 s（前台）/ ≤ 60 s（后台未被 ROM 冻结）。

**验收标准** 集成测试：中途 kill 进程后重启，从上一批续传且无数据丢失/重复。

**规格引用** §4.3、§4.4、§5.4.2

## T-251 Outbox

**预估** 2 人日 · **依赖** T-250, T-155

**交付物** Room 表 `sync_outbox(id, entity_type, entity_id, op, payload_json, attempt_count, next_attempt_at, last_error, created_at)` + flush 逻辑。

**实现要点**
- 同一实体的多次修改**入队时合并**（同 `entity_id` 的 pending upsert 只保留最新）。
- 重试：指数退避 `min(2^n * 5s, 30min)`，最多 10 次后标 `FAILED` 并在 UI 提示。
- **`4xx`（除 409/429）不重试**，直接 `FAILED` + **上报 Sentry**——说明是客户端 bug（例如 viewer 误为共享卡入队，服务端会 403）。
- 推送顺序：**先 `card` 后 `card_member`**，保证引用完整性。
- `sync_state` 状态机：`PENDING` / `SYNCING` / `SYNCED` / `FAILED`，UI 显示细微徽章。

**验收标准** 单测覆盖合并、退避曲线、4xx 不重试；仪器测试用 `TestListenableWorkerBuilder` 验证 WorkManager 集成。

**规格引用** §4.3、§5.4.3

## T-252 ConflictResolver

**预估** 2.5 人日 · **依赖** T-251

**交付物** 字段级三路合并（base / local / remote）+ 码值冲突副本流程。

**实现要点**
- 本地必须保存三份：`base`（上次同步成功的服务端态）、`local`（当前本地态）、`remote`（409 返回的服务端态）。**`base` 的持久化是前提**，容易漏。
- 合并算法：
  ```
  local[f] == base[f]   → 取 remote[f]（本地没改）
  remote[f] == base[f]  → 取 local[f]（对方没改）
  否则                  → 真冲突
  ```
- 真冲突且字段是 `barcode_value` / `barcode_format` → **必须触发冲突副本**：应用 remote 到原卡，同时用本地 `barcode_value` 新建一张卡，`title = "{原标题} (Konflikt)"`，**仅自己可见（不继承成员）**，弹说明对话框让用户自行取舍后删除多余的一张。
  - **为什么码值特殊**：title/color 改错用户能一眼看出并改回；码值改错、原值丢了，用户只能重新翻实体卡。**不可再生的数据不允许静默丢弃。**
- 其他字段真冲突 → 服务端赢（LWW by server revision），Snackbar：`„{title}" wurde auf einem anderen Gerät geändert.`
  - **文案是设备口径，不是人名口径**——共享卡只有 owner 能改，冲突方必然是自己的另一台设备。
- 无真冲突 → 用合并结果重试 `PATCH`（`If-Match = remote.revision`），**最多重试 2 次**。

**验收标准** 单测覆盖合并矩阵全部分支；码值冲突产生副本且原卡取 remote 值。

**规格引用** §3.5、§5.4.3、§16 R3

## T-253 四层同步触发

**预估** 1.5 人日 · **依赖** T-250

**交付物** 四层触发全部接入 `SyncEngine.sync()`：
1. **FCM data-only**（尽力而为，P50 < 3 s）——M2 先做**占位**，真实接入在 T-354
2. **App 进入前台**（`ON_START`）立即同步
3. **WorkManager 周期任务**：每 6 小时；`NetworkType.CONNECTED` 约束（网络恢复即触发）
4. **钱包页下拉刷新**（用户可控兜底）

**实现要点**
- 为什么要四层：FCM data-only 在 Doze 与小米/华为/OPPO 等激进省电 ROM 上**不保证送达**也不保证及时。若唯一触发器是 FCM，共享变更可能数小时不可见（R4，概率**高**）。
- 设置页提供"电池优化白名单"引导（`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`），文案说明用途（UI 在 T-450）。

**验收标准** 断网 → 恢复网络后 WorkManager 自动触发一次同步；四个入口都走同一个 Mutex 保护的 `sync()`。

**规格引用** §3.6、§4.4、§16 R4

## T-254 Glance Widget

**预估** 2 人日 · **依赖** T-153, T-154

**交付物** `widget/`：Glance `GlanceAppWidget`，2×2 / 4×2 / 4×4 三档尺寸。

**实现要点**
- **Widget 只显示卡名称 + 颜色/首字母图标，绝不渲染条码或码值**（T09：锁屏预览、他人瞥屏、截屏分享都会泄露会员号）。
- 点击 → `PendingIntent` 打开全屏条码页（若启用了应用锁，先过生物识别）。
- 数据源为 Room `Flow`，通过 `updateAll()` 刷新，**防抖 ≥ 5 s**。
- Widget 在无用户交互时读数据库——这正是 T-009 中 Keystore 密钥不设 `setUserAuthenticationRequired(true)` 的原因。

**验收标准** Macrobenchmark：Widget 点击 → 条码完全渲染 P95 ≤ 800 ms（冷启动 ≤ 1.8 s）；截图确认 Widget 上无码值。

**规格引用** §3.9、§9.1、§10.2

## T-256 Bootstrap 装载与 full_resync 处理

**预估** 1 人日 · **依赖** T-250, T-203

**交付物** 首次登录后的装载流程 + `409 full_resync_required` 的处理。

**实现要点**
- 首次登录顺序（§6.3.2）：`otp/verify` → `GET /v1/sync/bootstrap` → **写入 Room（单事务）** → 持久化 cursor → `PUT /v1/me/devices/{id}/push-token` → 进入钱包。
- `full_resync_required` → **清空本地库**后重新 bootstrap。清空前必须先 flush outbox 中的 pending 写入（否则丢失用户的离线修改），flush 失败的项要提示用户。

**验收标准** 服务端返回 409 后客户端能自动恢复到一致状态且不丢 pending 修改。

**规格引用** §5.4.1、§6.3.2

## T-257 同步收敛测试与离线端到端

**预估** 2 人日 · **依赖** T-252, T-256

**交付物**（§13.4-3 必须存在的高价值测试）
