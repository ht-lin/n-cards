## T-301 Friendship 模型与 username lookup

**预估** 1.5 人日 · **依赖** T-107, T-006

**交付物** `friendships` 表 + `GET /v1/users/lookup?username=<精确值>`。

**实现要点**
- `friendships` 规范化：始终 `user_low_id < user_high_id`（按 UUID 字节序），保证一对用户只有一行；`UNIQUE (user_low_id, user_high_id)`。`status`: `pending` / `accepted` / `blocked`。
- **lookup 只支持精确匹配**（`WHERE username = :normalized_input`）。**禁止**前缀匹配、模糊匹配、`LIKE '%x%'`、相似度排序。
- 结果只有两种：命中返回 **`{user_id, username}` 两个字段**，或 `404 not_found`。**绝不**返回邮箱、注册时间、好友数、卡数等任何附加信息——那才是把枚举变成情报收集的地方。**不返回候选列表、不返回"你是不是要找…"**。
- 服务端归一化输入：`trim` + `toLowerCase`（`Locale.ROOT` 语义）。
- 限流**双维度**：user 30/min + 300/day；IP 100/h（覆盖"批量注册 + 分摊枚举"）。两者都触发时返回**更长的** `Retry-After`。
- `Social` 通过 `Identity` 的 `UserDirectoryInterface::findByUsername()` 只读查询（不得直接查 `Identity` 的表）。

**注意** username 枚举（T18）是**有意接受的风险**：搜索功能不可能同时防枚举。**不要**把邮箱那套"恒定 202 + decoy"照搬过来——返回假的"找到了"会让功能不可用。

**验收标准** 契约测试；断言响应体**只有两个字段**；限流集成测试覆盖 user 与 IP 两个维度。

**规格引用** §3.8、§5.2、§6.2、§7.2 T18、§7.5

## T-302 好友请求生命周期

**预估** 1.5 人日 · **依赖** T-301, T-201

**交付物** `GET /v1/friends`、`GET /v1/friends/requests?direction=incoming|outgoing`、`POST /v1/friends/requests {user_id}`、`POST /v1/friends/requests/{id}/accept`、`/decline`。

**实现要点**
- `POST /v1/friends/requests` **只接受 `{user_id}`**（由 lookup 得到），**不再接受 `{email}`**——邮箱已彻底退出社交路径（C2）。
- 重复请求 → `409 already_exists`（幂等处理）。
- 限额：每用户每日发出好友请求 50；每用户好友数 500。
- 每次状态变更必须在同事务内写 `change_log`（audience = 双方）。
- **已移除的端点，若在旧契约/旧代码中出现必须删除，不得保留为 410**：`POST /v1/friends/invite-links`、`GET /v1/friends/invite-links/{code}`、`POST …/redeem`。

**验收标准** 契约测试；集成测试断言接受后双方 `GET /v1/friends` 均可见对方，且双方都收到 change_log。

**规格引用** §5.2、§6.2、§7.5

## T-303 解除好友 / 拉黑的级联撤销

**预估** 2.5 人日 · **依赖** T-302, T-305

> **这是 T20（权限残留）的唯一防线。**

**交付物**
- `GET /v1/friends/{userId}/shared-summary` → `{shared_by_me, shared_with_me}`（两个计数）
- `DELETE /v1/friends/{userId}`（解除）→ 响应回传 `{revoked_shares}`
- `POST /v1/friends/{userId}/block` / `DELETE` 同路径（拉黑 / 解除拉黑）
- `Sharing/Application/Port/ShareRevokerInterface::revokeAllBetween(userA, userB)`

**实现要点**
- **解除与拉黑执行完全相同的级联**，差别只在 `friendships` 行的去留（拉黑保留 `blocked` 行以阻止再次请求）。
- **必须在单一事务内**完成四步：
  ```sql
  1. UPDATE/DELETE friendships                     -- 解除 → 删行；拉黑 → status='blocked'
  2. UPDATE card_members SET left_at = now()
       WHERE left_at IS NULL
         AND ( (user_id = :a AND card_id IN (owner 为 :b 的卡))
            OR (user_id = :b AND card_id IN (owner 为 :a 的卡)) );   -- 双向
  3. UPDATE share_invitations SET status='revoked'
       WHERE status='pending' AND {inviter,invitee} = {:a,:b};
  4. INSERT change_log × N                         -- 成员墓碑，audience=[双方]
  ```
- **为什么必须同步 + 同事务**（不能用异步事件）：异步会出现"已非好友但仍能看到对方卡"的可见窗口，且两条 change_log 不在同一事务，客户端可能只收到其中一半。
- **双向**：Anna 可能既共享了卡给 Bob，也持有 Bob 共享的卡，两个方向都要撤销。
- **只撤销这一对用户之间的共享**：Bob 与 Carol 的共享、Anna 卡上其他 viewer 不受影响。
- 被移除方除成员墓碑外**还需要卡本身的墓碑**——否则他的 Room 里会留下一张没有成员关系的孤儿卡。
- 解除后重新加回**不会**恢复共享——owner 必须重新发起分享请求（UI 二次确认中写明）。

**验收标准** §13.4-5 好友解除级联测试（见 T-307）全绿，含"中途注入异常 → 全部回滚"。

**规格引用** §4.2、§5.2、§6.2、§7.2 T20、ADR-14

## T-304 ShareInvitation 与邀请端点

**预估** 2 人日 · **依赖** T-301, T-110

**交付物** `share_invitations` 表（**无 `role` 列**）+ `POST /v1/cards/{id}/invitations {invitee_user_id}`、`DELETE /v1/cards/{id}/invitations/{invId}`、`GET /v1/invitations`、`POST /v1/invitations/{id}/accept`、`/decline`。

**实现要点**
- **无角色选择**：被分享者恒为 `viewer`（C7）。请求体中**没有** `role` 字段。
- 发起时校验四项：① 调用者是该卡 owner（否则 `403 insufficient_role`）；② invitee 是 `accepted` 好友（否则 `403 not_friends`，经 `FriendshipCheckerInterface::areFriends()` **同步**查询）；③ 成员数 < 20；④ 无重复 pending 邀请（`409 already_exists`）。
- **接受时必须重新校验同样四项**（MUST）：① 双方**仍**是 accepted 好友；② 卡仍存在且未被 owner 删除；③ 邀请未过期/未撤回；④ 成员数未超限。邀请发出到接受之间可能间隔数天。**漏掉 ① 会让"解除好友"的级联撤销出现绕过路径。**
- 任一条件失效 → `409` 并把邀请置为 `revoked`/`expired`。
- 邀请**必须经接受**才生成 `card_members` 行。**不允许"直接塞卡进别人钱包"**。
- `expires_at` 默认 14 天。
- 限额：每用户每日发出共享邀请 100（T19 反复"分享→撤销"骚扰）。

**验收标准** 集成测试：发出邀请 → 解除好友 → 接受 → 返回 409 且邀请被置为 revoked。

**规格引用** §4.2、§5.2、§6.2、§6.3.3、§7.2 T19

## T-305 成员管理、权限矩阵与成员可见性裁剪

**预估** 2 人日 · **依赖** T-304

**交付物** `GET /v1/cards/{id}/members`（**按调用者角色在查询层裁剪**）、`DELETE /v1/cards/{id}/members/{userId}`（owner 移除 viewer，或 viewer 移除自己 = 退出）。

**实现要点 — 权限矩阵（服务端强制，不能只靠客户端自觉）**

| 操作 | owner | viewer | 非成员 |
|---|:---:|:---:|:---:|
| 查看卡 / 码值 / 全屏调出 | ✅ | ✅ | ❌ |
| 修改 title / color / merchant / note / expires_on | ✅ | ❌ | ❌ |
| 修改 barcode_value / barcode_format | ✅ | ❌ | ❌ |
| 修改**自己的** sort_order / is_pinned | ✅ | ✅ | ❌ |
| 邀请新成员（限已确认好友） | ✅ | ❌ | ❌ |
| 移除成员 | ✅ | ❌（只能移除自己＝退出） | ❌ |
| 自行退出 | ❌（owner 只能删卡） | ✅ | — |
| 删除整张卡 | ✅ | ❌ | ❌ |

- `PATCH`/`DELETE /v1/cards/{id}` 对非 owner **一律 `403 insufficient_role`**，即使请求体合法、revision 正确。
- **owner 不可移除自己** → `403`。
- **已移除的端点**（不得保留）：`PATCH /v1/cards/{id}/members/{userId}`（改角色）、`POST /v1/cards/{id}/ownership`（转让）。

**实现要点 — 成员可见性（C11，三层缺一不可）**
1. **API 过滤**：`GET /members` 对 owner 返回全部成员（含加入时间），对 viewer **只返回 owner + 自己两行**。**在查询层裁剪，不是返回全量再让客户端过滤。**
2. **同步层过滤（关键，见 T-201）**：`card_member` 变更的 audience 只含 `[owner, 当事人]`。否则 Bob 的 Room 里会直接躺着 Carol 的成员行——UI 过滤得再干净也没用，本地数据库已经泄露了。
3. **字段级过滤**：`Card.member_count` **只对 owner 返回**，对 viewer 省略。owner 需要它显示"共享给 N 人"与删卡前警告；viewer 拿到就等于知道还有几个人。

**为什么这是硬要求**：Anna 把家庭卡分别共享给伴侣 Bob 和同事 Carol，**Bob 与 Carol 可能互不认识**。授权链是两条独立的边，绝不构成 Bob↔Carol 的关系。暴露共同成员等于凭空创造一条社交连接（T21）。

**退出共享语义**：viewer 移除自己 → 只写 `left_at`，卡本身不变；owner 侧收到成员移除记录，viewer 侧收到**成员墓碑 + 卡墓碑**。

**验收标准** 见 T-307 的权限矩阵测试与成员可见性测试。

**规格引用** §5.2、§5.4.3、§6.2、§7.2 T13/T21

## T-306 FCM 集成与 Notification 模块

**预估** 1.5 人日 · **依赖** T-102, T-201

**交付物** `Notification` 模块的 `FcmSender` + Domain Event 订阅（`CardSharedWith` / `MemberRemoved` 等）+ `fcm_send_total` 指标。

**实现要点**
- **载荷固定为 `{"t":"sync","v":1}`**，纯 data-only，**不含任何个人数据**。禁止扩展这个载荷。
  - 理由：FCM 是美国数据处理方。若载荷含"Anna 分享了 PAYBACK 卡给你"，就把用户关系与消费偏好交给了 Google。因此 ROPA 中 FCM 的处理数据仅为「设备推送令牌 + 唤醒信号」。
- **通知文案全部由客户端在本地同步后自行生成**（T-354）。
- 推送经 Messenger **异步** Domain Event 发送——推送失败**不应回滚业务事务**。
- **禁止**集成 Firebase Analytics、Crashlytics（用 Sentry 替代）、Google Analytics 或任何广告 SDK。

**验收标准** 集成测试断言发出的载荷字节级等于 `{"t":"sync","v":1}`；推送失败不影响业务事务提交。

**规格引用** §3.12、§4.2、§4.4、§8.3、§17.3

## T-307 M3 强制测试套件

**预估** 2 人日 · **依赖** T-303, T-305

**交付物**（§13.4"必须存在的高价值测试"中属于 M3 的四条）

1. **权限矩阵测试**：`owner / viewer / 非成员` × 每个卡相关端点，参数化写，一个 data provider 覆盖**全部组合**。**不允许因为"只剩两种角色"就抽样。** 必须显式包含 `viewer × PATCH / DELETE / invitations → 403`。
2. **好友解除级联测试**：Anna↔Bob 互相共享若干卡，且各自与 Carol 有共享；解除 Anna↔Bob 后断言 ① 两人之间的共享全部 `left_at` 非空；② 与 Carol 的共享**不受影响**；③ 双方均收到成员墓碑；④ 待处理邀请被置为 `revoked`；⑤ **全部发生在一个事务内**（中途注入异常 → 全部回滚，不出现"好友已解除但共享还在"）。
3. **成员可见性测试（两层都要测）**：一张卡有 owner + 3 个互不为好友的 viewer；断言 ① `GET /members` 对 viewer 只返回 2 行；② **新增/移除第 4 个 viewer 时，change_log 的 audience 只含 `[owner, 该成员]`**——前 3 个 viewer 的 `/v1/sync` 结果中不出现任何与他人相关的 `card_members` 行；③ viewer 拿到的 `Card` 无 `member_count`。**第 ② 条是真正的防线，只测 ① 等于没测。**
4. **共享端到端**（`tests/Api`）：完整共享流程 —— 加好友 → 邀请 → 接受 → owner 编辑同步 → 移除成员 → 墓碑下发。

**验收标准** 四条测试全绿并纳入 CI 阻断门禁。

**规格引用** §13.4

## T-350 好友 feature（搜索 / 请求 / 列表）

**预估** 2.5 人日 · **依赖** T-301, T-302

**交付物** `feature:friends`：username 搜索、好友列表、收到/发出的请求列表、接受/拒绝。

**实现要点**
- **搜索必须是显式提交**：客户端**只能**在用户点击「搜索」后发起**一次**请求。**禁止** typeahead / 自动补全 / 边输边搜——任何 typeahead 都会把 username 空间变成可批量遍历的目录。
- 客户端同样做 `trim` + `toLowerCase(Locale.ROOT)` 归一化（**不得**用系统 locale——土耳其语 `I→ı` 会破坏匹配）。
- 未命中 → 显示"未找到该用户"，**不显示任何候选**。
- 命中 → 只显示 username + 「发送好友请求」按钮。用户**无法**在发请求前确认"是不是我认识的那个人"——这是可接受的：username 本就需要通过其他渠道从对方那里拿到（R14）。
- 429 → 显示限流提示并按 `Retry-After` 退避。

**验收标准** Compose UI Test：输入过程中无任何网络请求；点击搜索仅发一次。

**规格引用** §3.8、§6.2、§16 R14

## T-353 viewer 只读体验

**预估** 1.5 人日 · **依赖** T-352

**交付物** 共享卡的只读呈现 + 退出共享入口 + placement 上行。

**实现要点**
- **viewer 的共享卡在 UI 层即无编辑/删除入口**——**不是"点了才报错"**。服务端仍独立强制（双保险）。
- 共享卡**持久显示**「共享 · 只读」徽章 + 「von {username} geteilt」——使 viewer 始终知道该卡不属于自己、**可能消失**（这是 §3.7 删号硬删语义能成立的前提，也是 R9/R12 的缓解）。
- 徽章**不得以颜色作为唯一信息载体**（需带图标或文字，无障碍要求）。
- viewer 唯一可写的是自己的 `sort_order` / `is_pinned` → `PUT /v1/cards/{id}/placement`，**不参与 revision**。
- viewer 的"退出共享"= `DELETE /v1/cards/{id}/members/{myUserId}`，UI 文案是「退出」不是「删除」（R9）。
- **viewer 客户端不得为共享卡入 outbox**（placement 除外）。若因 bug 入队，服务端 403 会让它进 `FAILED` 并上报 Sentry。

**验收标准** UI Test 断言 viewer 视图无编辑/删除按钮；outbox 中不出现共享卡的 card upsert。

**规格引用** §3.5、§5.2、§7.3、§11.2、§16 R9

## T-354 FCM 接收与本地通知

**预估** 2 人日 · **依赖** T-306, T-253

**交付物** `FirebaseMessagingService` → 唤醒 `SyncEngine.sync()` → **同步完成后本地生成通知**。

**实现要点**
- 通知渠道：单一渠道组 + 三个渠道 `sharing`（共享相关）、`security`（新设备登录）、`sync`（**默认关闭**，仅调试）。
- Android 13+ `POST_NOTIFICATIONS`：**不在启动时索要**，而在用户**首次成功共享或接受共享后**，用一句上下文说明再申请。
- 通知点击 → 深链接到对应页面（好友请求 / 共享请求 / 卡详情）。
- **`sharing` 渠道必须覆盖六类事件，文案分开写**（后三类是 R12 的直接缓解，**不得**合并成笼统的"部分卡片已移除"——用户无法据此判断是不是 Bug）：

| 事件 | 文案要点 | 动作 |
|---|---|---|
| 收到好友请求 | "{username} 想加你为好友" | 打开好友请求页 |
| 收到共享请求 | "{username} 想与你共享一张卡" | 打开邀请详情 |
| 自己的共享被接受/拒绝 | "{username} 已接受/拒绝你的共享" | 打开卡详情 |
| **卡被 owner 删除** | "「{title}」已被 {username} 删除" | 无 |
| **被移除成员 / 自己退出** | "你已不再拥有「{title}」的访问权限" | 无 |
| **因解除好友而失去** | "与 {username} 解除好友后，你们之间共享的 N 张卡已移除" | 打开好友列表 |

- 生成"卡消失"类通知需要在删除本地行**之前**读出 title 与来源 username——顺序容易写反。
- 所有文案在 `strings.xml`，德英双语，复数用 `plurals`。

**验收标准** 六类事件各有一条本地化通知的仪器测试；FCM 送达后 P95 ≤ 10 s 内前台可见变更。

**规格引用** §3.12、§10.3、§16 R12
